# W2.8 · Member Home + Rhythm

Build blueprint for the biggest item left in Phase 2. Behavioral truth is `10` and `07`; the
data is `02`. This doc carries what the backend session landed, the contract the screens draw
from, the decisions taken with Ayo, and the gate that blocks two of the screens. **Delete once
W2.8 lands.**

## What landed (backend, 2026-08-07)

Migration `20260807120000_the_rhythm_domain.sql` and pgTAP `030` (49 assertions). All of it
verified against the local stack, including a live run of the weekly job through pg_cron.

| Object | What it is |
|---|---|
| `attendance` | One row per member per day. `service_date` is derived by trigger and immutable afterwards; the table has no UPDATE path at all |
| `streaks` | Derived cache, server-owned. Readable by its owner, writable by nobody |
| `milestones` | Server-owned, `unique(profile_id, kind)`, so awards are `on conflict do nothing` |
| `attendance_service_date(instant, zone)` | **The only place a timezone is applied in the domain.** Its own function so the DST cases can be asked about at all |
| `rhythm_week(date)` | The Monday of that ISO week. Pure date arithmetic |
| `recompute_streak(profile)` | Full recompute from immutable rows. Idempotent |
| `rhythm_state(branch)` | **The read path for every screen** (see below) |
| `record_attendance(branch, taken_at)` | "I'm here", idempotent, answers with the resulting rhythm |
| `recompute_all_streaks()` | Weekly safety net, behind the `streak-recompute` job (Mondays 03:40 UTC) |

## The contract the screens draw from

`rhythm_state(p_branch_id)` answers for `auth.uid()` and takes no profile id, so there is no
foreign id to probe. It returns one row:

| field | meaning |
|---|---|
| `today` | The date **in the browsed branch's timezone**, decided by the server |
| `checked_in` | Whether this member already has attendance for that date |
| `state` | `none` / `active` / `grace` / `lapsed` |
| `current_weeks` | The live streak: 0 when lapsed |
| `longest_weeks` | Monotonic; never taken away |
| `last_service_date` | For the history header |

`record_attendance(p_branch_id)` returns the same shape plus `recorded`, which is false when
the member had already checked in. **Both the toast and the streak strip come from that one
answer.** Do not compute "today" in the app, do not read `streaks` directly for the number on
screen, and do not keep a local "checked in" flag beside the server's: W2.4 cost four
device-only bugs to exactly that shape, and here the client's clock is the thing being
distrusted in the first place.

RHYTHM's history and milestone list are plain RLS-scoped selects on `attendance` and
`milestones` (own rows only, oldest-first paging is the app's choice).

## Decisions taken with Ayo (2026-08-07)

1. **Grace covers one missed week; two start a new run.** `02` said "consecutive ISO weeks",
   `10` said a missed week pauses and resumes. `10`'s promise won, both docs are corrected, and
   the maths lives in `recompute_streak`. Four weeks, a hard Sunday, then back reads as five.
2. **Content milestones are awarded on APPROVAL, not on submission** (decided while building).
   Celebrating a post that a moderator then rejects is the opposite of what `10` asks for.
   `first_testimony` and `first_prayer` are triggers on the status change; the plan milestones
   belong to W4.4.
3. **Backend first, screens in a fresh session**, because the screens are partly blocked (below)
   and the date maths deserved its own sitting.

### What the frames decided

1. **Lapsed leads with the longest, never with 0.** `rhythm_state` returns `current_weeks = 0`
   when lapsed, and a 58px gold **0** is exactly the scold `10` forbids. The hero reads
   `11 · weeks, your longest`. The Home strip's ring disappears in `none` and `lapsed`, because
   the ring is progress toward the next milestone and there is no run in progress.
2. **The grace week is not drawn in the attendance history.** A "you missed this one" row means
   the app working out which week has no row, which is the streak maths creeping back into the
   client. Grace is said once, from `state = 'grace'`: in the hero copy and one quiet gold
   banner (`.linkbanner.gold`, the shape W2.7 made for a line you may ignore).
3. **Checked-in quietens, it does not vanish.** The gold "I'm here" becomes tinted gold with a
   gold hairline and a check, the treatment `.glory.on` and `.glorybig.on` already use for a
   reaction already made, and keeps its place in the row so the card still states plainly that
   today is handled.
4. **The celebration is centred, not a bottom sheet.** A sheet's shape asks for a decision; this
   announces. The disc is AUTH-4's arrival disc and the burst is `components/ui/Burst`'s six
   dots, so the reduced-motion variant is the contract `Burst` already keeps: the dots are not
   rendered at all and the overlay simply arrives still.
5. **"Share the joy" stays** (`10` calls the share optional). It is text-only through the
   existing `features/family/share.ts` `shareText`, not a rendered image: a branded milestone
   image would be new work for no asked-for gain.
6. **RHYTHM's devotional section is omitted until W4.4.** The approved active-state frame ends
   with a "Living Loved · Day 8" card; there is no plan to route to yet, and `07`/`10` forbid
   routing to an empty PLAN. It appears when W4.4 lands.

One new component falls out of this and belongs in `src/components/ui`, not in a screen: the
celebration overlay (dim + centred card + focus trap + the reduce-motion branch). Everything
else composes from existing primitives.

## The ladder that does not end (decided with Ayo, 2026-08-08)

`4, 12, done` is a dead end, and RHYTHM found it: past twelve weeks the "Next" card disappears,
the ring sits permanently full, and the app never celebrates that member again. The retention
loop goes quiet exactly for the people who show up most. `10` lists those two rungs as
"Examples", so this extends the spec rather than contradicting it, and `10` is updated in slice
5's PR.

**Deliberately NOT Duolingo's engine.** Duolingo runs on loss aversion: freezes, repair offers,
"don't lose your 400 days". `10` names that as the thing to avoid. What is being copied is the
ENDLESSNESS, not the anxiety, and the difference is made mechanical: **the badges you hold can
never come off**, because every award is `unique(profile_id, kind)` and a rebuilt streak
therefore neither re-celebrates nor un-celebrates anything.

Two layers, both agreed:

1. **Eternal week rungs.** 4, 12, 26, 52, then one per year without end. There is always a next
   rung, so the ring always has somewhere to go and the "Next" card never vanishes. Streak-based,
   so it does still reset after two missed weeks (grace covers one).
2. **Cumulative gatherings.** The 10th, 25th, 50th, 100th Sunday and on, counted across a
   member's whole time here rather than consecutively. A lapse costs nothing: someone back after
   six months away is still climbing. This is the layer Duolingo has no answer for, and the one
   that best fits "a streak is a gift, not a debt".

A third layer, a **belonging anniversary** ("one year since your first Sunday"), was offered and
NOT taken. Do not add it without asking.

**Named in church language, not counted.** "A month of Sundays", "A season with us", "Half a
year", "A year of Sundays", then `{{count}} years of Sundays` generated for every year beyond
the named tiers; the cumulative ones read "Your 50th gathering". Glyphs follow the frames'
vocabulary (🔥 at four weeks is already drawn; 🌟 🕊️ 👑 💛 for the rungs above).

Three things whoever builds it should know before starting:

- **The kind must become parseable.** `features/rhythm/milestones.ts` holds a fixed catalog today
  and deliberately drops any kind it cannot name, which is right for a finite ladder and wrong
  for an endless one. Week rungs become `<n>_week_rhythm` and gatherings `<n>_gatherings`, with
  the label derived from `n`; only the truly named kinds (`first_service`, `first_prayer`,
  `first_testimony`) stay in a lookup.
- **The trigger stops testing two numbers.** `attendance_after_insert` currently asks
  `if weeks >= 4` and `if weeks >= 12`. It should award every rung at or below the current run
  and every gathering count reached. That is idempotent by construction (`award_milestone` is
  already `on conflict do nothing`) and therefore self-healing: a grace week that jumps the run
  forward awards whatever was skipped.
- **"Your 50th gathering" is an ORDINAL**, and ordinals are not plurals. i18next has
  `_ordinal_one`/`_ordinal_other` forms; DE writes "50." and FR "50e". Decide this in the copy,
  not in a component.

## Notes for whoever picks it up

- **Live-watch attendance credit is W3.2**, not this item. The `live_watch` source exists in the
  enum and nothing writes it yet; note it and move on.
- **The offline queue already covers attendance** (W2.4 built the queue for glory, intercession,
  RSVP, attendance, plan-complete and playback). "I'm here" is a queued write, and the 72-hour
  clamp exists precisely so a Sunday tap replayed on Monday still records Sunday. Use
  `client_taken_at` from the tap, never from the replay.
- **Seeded rhythm exists on the local stack**: Grace has a grace-covered five-week run, Tobi has
  one week, Marieke lapsed a month ago with her longest remembered. Those are the three states
  the screens must render, so the device pass has real data the moment `pnpm db:reset` finishes.
- **Grace-framed copy matters more here than anywhere else in the app.** A pause is never a
  scold, `lapsed` is never a failure, and the number that leads is the one that encourages.
