# W2.7 · Dashboard foundation + Phase A: moderation + verses

Build blueprint for the first item that is not the mobile app. Behavioral truth is
`17-ADMIN-DASHBOARD.md`; the authorization rule is `17` §Platform; the test bar is `21`
§4. This doc adds sequencing, the findings from reading the current Next and Supabase
docs first-hand (2026-07-28), and the decisions that need Ayo before code. Delete once
W2.7 lands.

Why now, ahead of W2.5 and W2.6: both of those have Done criteria that require approving
content, and there is nothing to approve with. `25` already says to build W2.7 "in
parallel with W2.3-2.6 and no later"; we have reached the point where "no later" bites.

## What exists today

Almost nothing, which is the honest starting point. `apps/dashboard` is the W0.4
scaffold: Next 16.2.10, React 19, Tailwind 4, Vitest, a blank page, and one harness test.
No Supabase client, no auth, no components, no routes. `packages/shared` already carries
the design tokens and the generated database types, and the ESLint/Prettier/CI wiring
covers the dashboard already.

What DOES exist is the whole server-side foundation this module drives: `testimonies` and
`prayers` with their status machine, the compare-and-set rule, `reports`,
`can_moderate_branch()`, `caller_is_admin_live()`, and the moderation policies. W2.7
writes almost no new SQL; it builds the surface that finally exercises what W1.5 and W2.3
already enforce.

## Findings that change the shape (read first-hand, 2026-07-28)

### 1. "Middleware" in `17` must not be Next's middleware

`17` §Platform says "centralized middleware on EVERY server route derives the caller from
their session JWT, loads role + branch server-side, and authorizes the specific action +
target BEFORE any service-role call."

Next 16 renamed `middleware.ts` to **`proxy.ts`**, and its own docs are explicit that this
layer "should not be used as a full session management or authorization solution" and
"should not be your only line of defense in protecting your data", because it runs on
prefetched routes and must stay cookie-only for performance. The pattern they prescribe
instead is a **Data Access Layer**: authorization checked as close to the data as
possible, in a module every route calls.

The spec's INTENT is exactly a DAL, so nothing about the requirement changes. The word
does, and left alone it would send an implementer to the one place Next says not to rely
on. `17` should be reworded in this PR: a centralized `authorize()` that every server
route awaits before touching data, with `proxy.ts` used only for an optimistic redirect of
signed-out visitors, never as the check.

### 2. Supabase passkeys are real, and experimental

`17` requires "passkeys/WebAuthn on the dashboard, mandatory for admins", and
`~/.claude/standards/security.md` requires phishing-resistant MFA for staff access.

Supabase Auth now ships passkey support natively (`supabase.auth` WebAuthn ceremonies,
discoverable credentials, relying-party config in the dashboard). Two caveats from the
docs, verbatim in substance:

- it is marked **experimental**: "the API may change without notice", and the client must
  explicitly opt in when constructed;
- it needs `@supabase/supabase-js` v2.105.0+. The repo is on 2.110.7, so that is met.

That is a genuine risk decision rather than a detail: the highest-privilege accounts in
the ministry would sign in through an API the vendor reserves the right to change. It is
Ayo's call (see Open questions), not a default to be assumed either way.

### 3. Session handling is `@supabase/ssr`, not the mobile client

The mobile app's client is built around `LargeSecureStore` and AsyncStorage. The dashboard
needs cookie-based sessions readable by server routes, which is `@supabase/ssr`'s
`createServerClient` / `createBrowserClient` split. That is two new dependencies for
`apps/dashboard` (`@supabase/supabase-js`, `@supabase/ssr`) and needs confirming at add
time per the project rules.

### 4. Enrolling a factor does nothing on its own

Checked because the plan recommended TOTP without saying where it is enforced, which is
the kind of gap that ships a decorative second factor.

MFA factors in Supabase are **account-level, not app-level**. Once a leader enrols TOTP
for the dashboard, every client signing that account in gets `currentLevel: aal1` and
`nextLevel: aal2`, including the mobile app.

Two consequences, and the second is the one that matters:

- **The mobile app is not broken by this.** Its session stays valid at `aal1`, and no RLS
  policy in this project requires `aal2`, so a leader keeps using the app exactly as
  before. The app simply never offers the challenge it now technically could. That is
  acceptable for Phase A and should be a conscious note rather than a discovery later.
- **The dashboard must enforce `aal2` itself, or the factor is decorative.** Enrolment
  alone changes nothing: a leader could sign in to the dashboard with email OTP only, sit
  at `aal1`, and moderate. So `authorize()` requires `aal2` on every dashboard route, and
  the sign-in flow presents the TOTP challenge when `nextLevel` exceeds `currentLevel`.

**Do NOT reach for the docs' restrictive-RLS pattern here.** Supabase's guide shows
`as restrictive ... using (auth.jwt()->>'aal' = 'aal2')` applied to a table. On these
tables that would hit the MOBILE app's members too, and lock every member out of their own
content the moment any of them enrolled a factor. Enforcement belongs in the dashboard's
route layer, which is the only place that knows the request is a dashboard request.

## The shape of the authorization layer

This is the part worth getting right, because everything else is CRUD around it.

- **One module**, `src/server/authorize.ts`, exporting a single entry point that every
  route awaits. It resolves the caller from cookies, loads `role` and `branch_id` from
  `profiles` SERVER-SIDE (never from the JWT claims alone, which go stale on demotion,
  and never from the request body), and answers a specific question: may THIS caller take
  THIS action on THIS target.
- **Service-role is the exception, not the transport.** `17` says prefer the caller's own
  JWT plus RLS wherever possible. Moderation genuinely needs elevation (a leader has no
  RLS path to another member's pending row), so those routes use it; everything readable
  through RLS goes through the caller's client, so the database keeps checking our work.
- **`aal2` is part of the answer, not a separate check.** `authorize()` refuses a caller
  whose session has not cleared its second factor, alongside refusing the wrong role or
  the wrong branch. One place, one verdict.
- **The tests are the deliverable, not the routes.** `21` §4 wants "foreign-id IDOR probes
  on dashboard routes" in pgTAP, plus CI probes per route. A leader touching another
  branch must fail in a test, not merely be absent from the UI.

## The test harness, which does not exist yet

`apps/dashboard` has Vitest and one harness test: no DOM environment, no React testing, no
way to exercise a route. Asserting "IDOR probes in CI" without this is asserting an
outcome with no mechanism, so slice 1 builds it.

- **Route handlers need no special harness.** A Next route handler is a plain function
  from `Request` to `Response`, so a test imports it and calls it. That is the whole
  trick, and it is why the probes are cheap once the session part is solved.
- **Sessions come from the real local stack, not a mock.** The lesson from W2.4 is that a
  test which mocks the thing under test proves only the mock. These tests mint real tokens
  against the local Supabase (admin API, as this session already did by hand for
  photo-guard) and pass real cookies, so `authorize()` is exercised against real JWTs and
  real `profiles` rows. Only genuinely external things get mocked.
- **Components** need `@testing-library/react` plus a DOM environment (`jsdom` or
  `happy-dom`) wired into `vitest.config.ts`, and an axe run for the accessibility pass
  the frontend standard requires. This is the project's first keyboard surface, so that
  pass is real work, not a checkbox.
- These are dev dependencies for `apps/dashboard` and need confirming at add time.

## Slices

Sized so each one is verifiable on its own. `25` marks the item multi-session; this is
where the sessions fall.

**Slice 1: sign in, and prove who you are** (`feat/w2-7-dashboard-auth`)
- `@supabase/ssr` client trio (browser, server, and a service-role client that lives in
  one file and is never imported by a component).
- Email OTP sign-in reusing the same identity as the app, plus whatever MFA answer Q1
  gives. Non-leaders are refused at the door with an honest message, not a blank page.
- `authorize()` with its unit tests, and a `/` that shows who you are and which branch you
  moderate. Nothing else. The point of the slice is that the authorization layer exists
  and is tested before anything valuable sits behind it.

**Slice 2: seeing the queue** (`feat/w2-7-moderation-read`)
- The `dashboard.html` moderation frame first, approved before any screen code.
- Pending testimonies and prayers, branch-scoped for leaders and global for admins, with
  the photo (signed URL; leaders can already read pending photos per W2.3).
- Read-only, and that is the point: the hardest part of the queue is scoping, and scoping
  is provable without any write path existing. The IDOR probes land here, against a
  surface that cannot yet do damage.

**Slice 3: acting on it** (`feat/w2-7-moderation-act`)
- Approve / Reject-with-reason / Remove, each carrying the reviewed `updated_at` so the
  compare-and-set in `02` can refuse a stale decision, with the "content changed since
  review" path surfaced honestly rather than swallowed.
- The safeguarding guideline in the UI copy where the decision is made, not in a wiki
  (`17` §1, `20`).
- This is the slice that unblocks W2.5 and W2.6.

**Slice 4: reports inbox + daily verses** (`feat/w2-7-reports-verses`)
- Reports inbox: review flagged content, action or dismiss, re-report is a no-op.
- Daily-verse CRUD plus the CSV batch import (`22` §1 quarterly 90-day batches). Verses
  cannot wait: `17`'s phasing note calls them out as the reason Phase A is not just
  moderation.

**Slice 5: the freshness safeguard** (`feat/w2-7-escalation`)
- Moderation notifications to leaders (in-app/email until push lands in Phase 3) and the
  48h escalation job. Needs the scheduler (`21` §5: Supabase Cron, pg_cron + pg_net,
  every job ends by pinging its healthchecks.io dead-man check).
- Deliberately last: it is the only slice that adds infrastructure, and W2.5/W2.6 are
  unblocked once slice 3 lands.

   than assumed, so it was checked twice: the live docs still carry the experimental
   caution and the literal client opt-in, and the changelog shows passkeys went **beta on

   **This is a KNOWN GAP against `17` and `~/.claude/standards/security.md`**, both of

2. **The first admin is seeded by migration**, named to Ayo's app address. Production gets
   its first admin the same deliberate, audit-visible way at the W2.7 deploy.
3. **One frame, for the moderation queue.** `entry-flow.html` is a phone mockup and the

   the reports list are conventional layouts and get none: the queue is where a leader
   spends their time and the only screen with real density decisions to make.

## Finding 3: nothing creates a profile but the member

There is no `handle_new_user` trigger on `auth.users`. A profile is created by the member
themselves at AUTH-3, through the `members create their own profile` policy whose WITH
CHECK pins `role = 'member'`; and `profiles_update_guard` then refuses any role change by
its owner ("role is immutable to its owner").

So a seeding migration cannot simply UPDATE a row that does not exist yet, and it cannot
be written as something the account does to itself, because both of those are load-bearing
rules rather than obstacles. The shape that respects them:

- a tiny `bootstrap_admins(email)` table, seeded in the migration and readable by nobody
  through the API;
- an AFTER INSERT trigger on `profiles` that promotes a new row whose email is listed,
  running as SECURITY DEFINER and announcing itself to the update guard through a
  transaction-local flag, exactly as `agbc.counter_write` already does for the counter
  triggers;
- the same promotion applied to an existing row if there is one, so order does not matter.

The alternative, relaxing the role-immutability guard, is worse: it would weaken the rule
that stops a member promoting themselves in order to solve a bootstrapping problem.
