# W4.12 · Dashboard hardening: navigation, loading states, feedback

**Status:** PLANNED 2026-09-10, from Ayo's report that the dashboard "feels like it lags, it
doesn't feel like a single page app, sometimes I click and I wait". Six slices, one PR each,
plus one separate bug fix that is not part of the item.

**The finding underneath the report: the dashboard has no client-side navigation at all.** It
is not a slow SPA. It is a set of independently server-rendered documents, and every rail
click is a full browser page load. The rail is a raw `<a href>` (`DashboardShell.tsx:231`), and
so are the moderation filter chips, the People links and the branch-request links. Nothing in
`apps/dashboard/src` has ever used `useTransition`, `useOptimistic`, `startTransition` or
`useRouter`, and there is no `loading.tsx`, no `Suspense` and no skeleton anywhere in it.

**This is the dashboard's missing W4.7.** That item ("Hardening audit: states, a11y,
performance, tablet", `25`) swept the mobile app only: its six slices are all `apps/mobile`.
The dashboard has never had a performance, navigation or loading-state pass, while `25` §4
item 4, which §5 inherits for dashboard work, has required all four data states of every data
surface since it was written. Nine dashboard screens have none of them.

**Next.js 16 names this exact failure in its own shipped docs**, which is worth quoting
because it is the whole diagnosis in one line. `node_modules/next/dist/docs`
`01-app/01-getting-started/04-linking-and-navigating.md:90`: "waiting for a server response
before navigation can give the users the impression that the app is not responding". Its
prescription at `:173`: "We recommend adding `loading.tsx` to dynamic routes to enable partial
prefetching, trigger immediate navigation, and display a loading UI while the route renders."
And at `:162`: "Client-side transitions are what makes server-rendered apps *feel* like
client-rendered apps."

**Refs:** `17` (the dashboard spec) · `21` §2-4 · `25` §1, §5, §6, §8 ·
`design/mockups/dashboard.html` (the four loading frames) ·
`~/.claude/standards/frontend.md` · Next 16's shipped docs at `node_modules/next/dist/docs`

---

## 1. What was measured, not assumed

**696 KB raw / 208 KB gzipped of JavaScript loads on every page.** Measured from
`.next/build-manifest.json` `rootMainFiles` against a real `pnpm build`, not estimated. The
largest chunk in it is 414 KB raw / 128 KB gz and carries Sentry's browser SDK. Because the
rail is an anchor, all of it is re-parsed and re-executed on every module switch.

**All 31 routes are `force-dynamic`,** confirmed in the build output (every route prints `ƒ`).
Per Next 16's `01-app/02-guides/prefetching.md`, a dynamic route is **not prefetched at all**
unless it has a `loading.js`, and its client cache TTL is **off by default**. So `<Link>`
alone would not have fixed this. The loading boundary is what makes prefetching work, and it
is the half that is missing.

**Three filter-chip sets are already `<Link>`** (`academy/page.tsx:282`,
`verses/Schedule.tsx:274`, `sermon-audio/Shelf.tsx:89`) **and still feel like full loads**,
because with no loading boundary and no transition React blocks on the RSC fetch while showing
nothing. That is the proof that the two halves are independent, and it is why this item does
both.

**Auth is 2 serial round trips, not 3.** `mfa.getAuthenticatorAssuranceLevel()` turned out to
be a local JWT decode (`@supabase/auth-js` 2.111, `GoTrueClient.js:5011`), so it is free. The
two paid ones are `authorize.ts:380` `getUser()` and `:391` the `profiles` select. Most pages
are 3 waves total; the worst are 6 (`/reports`, `/branches/[slug]/close`).

**A correction worth recording, because it removes a slice.** `proxy.ts:21-23` claims
`getClaims()` is "a local signature check", and `@supabase/auth-js` does fall back to a network
`getUser()` when `header.alg` starts with `HS`, so this was first read as a third hop on every
request including every prefetch. It probably is not one: both `agbc-production` and the local
stack publish an **ES256** key at `/auth/v1/.well-known/jwks.json` and no symmetric key.
Nothing in `docs/` records signing keys being enabled, so the state is undocumented rather
than known. Slice 1 settles it by decoding one live token's `alg`, and `credentials.md`
records the answer either way.

## 2. What the spec forbids, and what it demands

**Forbidden: "fixing" the auth round trips.** `17` line 13 requires `authorize()` to confirm
the session with the auth server, "`getUser()`, not a locally-decoded `getClaims()`, so a
signed-out or revoked session dies immediately rather than at token expiry", and `02` line 41
generalises it: authority is read from the live table, never from a JWT claim. `authorize.ts`
is not touched by this item. The two waves stay, and the next session should not re-propose
this.

**Demanded: the four states.** `25` §4 item 4: "Every data surface implements the four states
(loading skeleton, empty with CTA, error with retry, offline/cached)". `18` line 77 says it
again. The dashboard has error boundaries (`app/error.tsx`) and some empty states, and zero
loading states. Slice 5 is not an enhancement, it is an overdue requirement.

**Four loading frames are already drawn and approved, and have never been built:**
`QUEUE-LOADING` (`dashboard.html:2028-2059`), `VERSES-LOADING` (`:970-1012`),
`SERMON-AUDIO-LOADING` (`:1705-1747`), `REGISTRATIONS-LOADING` (`:4220-4265`). Six screens
have no loading frame at all (`/reports`, `/people`, `/people/requests`, `/broadcasts`,
`/events`, `/branches`), so those get composed and approved before any code, per the
mockup-first rule. `dashboard.html:239-244` says conventional layouts get no frame, but the
REPORTS comment at `:2112-2118` already overturned that reasoning once ("Both are density
decisions, which is what earns a frame").

**The skeleton rules, stated three times in the mockup and worth carrying:** stat numbers are
skeletons and **never zeros** ("a '0 German' that turns into '88' a second later is the one
wrong number this screen must never print"); actions are **hidden while loading, never
disabled**, so there are no dead buttons under skeletons; and **offline is the one state where
an action IS disabled rather than hidden**. The `.skel` gradient (`dashboard.html:153-154`) is
a **static three-stop gradient, not a shimmer**: there is no `@keyframes` or `animation`
anywhere in that file.

**A deliberate departure from the frontend standard, recorded rather than silent.** Ayo's call
on 2026-09-10 was to drop the no-JavaScript fallback as a constraint, because this is a staff
tool. `~/.claude/standards/frontend.md` asks that core tasks work with HTML alone "wherever
the product allows", and this decides that the product does not require it here. What it buys
is in the deferred list: an action may return data rather than redirecting, which is what
optimistic updates need. Slice 2 and 3 do not yet spend it.

## 3. The controls that say nothing when clicked

Listed separately because this is the cheapest fix in the item and the most directly felt.
**The moderation Approve, Reject and Remove have no pending state at all**
(`QueueActions.tsx:38,:61,:96`), on the busiest surface in the product, while
`SubmitButton.tsx:16-22` names that very queue as the reason it was written. It was never
wired up. The same is true of branch-request Approve (`RequestCard.tsx:52`), Refuse
(`RefuseForm.tsx:61`), Remove audio and Remove picture (`sermon-audio/[id]/page.tsx:204,:324`)
and Sign out (`PageHeader.tsx:32`, `page.tsx:75`). Three `useActionState` call sites discard
the pending flag by destructuring only two elements (`AttachPanel.tsx:59`,
`NewMessagePanel.tsx:44`, `ConfirmForm.tsx:50`), and `VerseForm.tsx:203` greys Remove out
while only the *other* button's label changes.

## 5. What slice 4 does and does not buy

`git mv` of academy, branches, broadcasts, events, moderation, people, reports, sermon-audio
and verses into `src/app/(dashboard)/`. Route groups do not change URLs, so no route moves and
`25` §5's IDOR-probe-per-route rule adds nothing. `/`, `/sign-in`, `/mfa` and `/auth` stay at
the root: `/` uses `AuthShell` and redirects to `/moderation`, and the other three must not
show the rail.

`DashboardShell` is currently invoked **41 times across 24 page files**, each threading
`caller` and `current`. The layout takes it over, the rail becomes a client component reading
`useSelectedLayoutSegment()`, and `current` stops being a prop. `createServerComponentClient`
gets wrapped in React `cache()` so the layout and the page share one client instance, which
makes `authorize()`'s existing `WeakMap` (`authorize.ts:353`) dedupe across both. `cache()` is
per-request, so this does not violate the module-scope warning `server.ts` carries.

**What it does NOT buy: this does not halve auth per navigation.** Pages still call
`authorize()` for their own action, and that still runs on every soft navigation. What it does
buy is that the rail survives navigation instead of being torn down, that `loading.tsx` renders
inside the shell rather than blanking it, and that the year-wide `loadBranchRequests` scan is
paid once per hard load instead of on three separate pages.

**A consequence to accept rather than discover:** Next preserves layouts across soft
navigation, so the People badge will not refresh after a decision unless told to. The
branch-request actions call `revalidatePath('/', 'layout')`.

**The real risk in this slice is six absolute imports crossing the new boundary**, above all
`vi.mock('@/app/reports/actions')` at `ReportedCard.test.tsx:17`: a `vi.mock` path that no
longer resolves fails silently rather than red. The others are `ImageField.test.tsx:10`,
`ImageField.tsx:12-14`, `QueueActions.tsx:1`, `ReportedActions.tsx:1` and
`events/actions.ts:16`. Test discovery itself is safe: `vitest.config.ts` includes `src/**`,
and `next/link` is unmocked and already renders in jsdom across six existing UI test files.

## 6. Deferred, and tracked here so it is not rediscovered

**Waterfalls.** `signPhotos` (`moderationQueue.ts:110`) sits after a `Promise.all` it could
join. `await countResolvedThisMonth` inside object literals (`reportsInbox.ts:108,:177`). Two
awaits in one JSX props object (`sermon-audio/[id]/page.tsx:99,:101-105`). `/branches/[slug]`
and `/hq` re-read the same branch row, the same services and every profile twice, and `/close`
scans `profiles` three times, all so `/branches/[slug]` can compute `all.find(r => r.isHq)`.
`/broadcasts/new:43-47` selects a branch name `authorize()` already fetched as
`caller.branchName`. `reports/actions.ts:43,:53` each independently re-run `branchOf` plus
`authorize`, which is 8 round trips for one button. `verifyStepUp` is 3 on its own. The
`moderation_queue` view is a UNION, so PostgREST cannot embed through it, and 3 of that page's
waves exist because of its shape.

**Unbounded queries.** `branches.ts:283-290` reads **every live profile in the ministry** and
counts them in JS. `events.ts:138-146` reads **every event ever**, then splits past from future
in JS. Also `moderationQueue.ts:78-91`, `reportsInbox.ts:91-97`, `broadcasts.ts:169`,
`branches.ts:244-252` and `:558-561`. Exactly one true N+1 exists in the dashboard:
`branches.ts:582-586`, one RPC per future event.

**Client.** `useOptimistic` on the moderation and reports queues, which the no-JS decision now
permits. Retiring the `?outcome=` redirect pattern in favour of action return values. Getting
Sentry off the critical path (128 KB gz on every page, against the frontend standard's rule
that third parties never get the main thread first). `experimental.staleTimes`, which would
give dynamic segments a client cache (still experimental in 16.2.12, and `dynamic` defaults to
0). `<Suspense>` streaming. `useLinkStatus` for nav progress. A JS budget in CI, which the
frontend standard requires and this app has never had.

**Other defects found while mapping.** A controlled `<textarea>` holding a ~360-row paste
(`ImportPanel.tsx:119-132`), re-rendering the panel per keystroke. A fresh
`Intl.RelativeTimeFormat` constructed per row (`QueueItem.tsx:85`, `RequestCard.tsx:150,:164`,
`ReportedCard.tsx:125,:135`). `MfaEnrolForm.tsx:35-78` runs a multi-request effect at mount
with no skeleton. `key={attempt}` remounts whole forms on a refusal (`BranchForm.tsx:92`,
`EventForm.tsx:89`, `Composer.tsx:60`), including a 17-field form with two repeatable lists.

## 7. Slice 1: the baseline, measured 2026-09-10

`next start` on a production build, against the local Supabase stack, signed in as
`dev.grace@example.test` (the seeded leader, and the only staff account the local stack has),
warm cache, one hop per rail row. Automatic prefetching runs only in production builds, so
`next dev` could not have produced these.

| navigation | TTFB | DCL | load | doc | reqs | JS decoded | JS transferred |
|---|---|---|---|---|---|---|---|
| `/reports` | 169 ms | 183 | 220 | 8.3 KB | 14 | 810 KB | 0 |
| `/events` | 237 ms | 264 | 334 | 8.4 KB | 15 | 815 KB | 2 KB |
| `/broadcasts` | 147 ms | 165 | 227 | 7.5 KB | 15 | 812 KB | 1 KB |
| `/people/requests` | 172 ms | 191 | 240 | 8.0 KB | 14 | 810 KB | 0 |
| `/moderation` | 244 ms | 265 | 324 | 8.2 KB | 14 | 810 KB | 0 |
| `/moderation?kind=testimony` | 155 ms | 174 | 206 | 8.3 KB | 14 | 810 KB | 0 |

**All six report `navType: "navigate"`.** That is the proof rather than the inference: every rail
click and every filter chip is a full browser document load, not a client transition.

**810 KB of JavaScript is decoded on every navigation while 0 bytes are transferred.** The
chunks all come from disk cache and are all re-executed, along with a full DOM teardown and
rebuild. An RSC probe of the same routes returns **12 to 15 KB**, which is what a client
transition would move instead.

**Four readings that matter more than the averages:**

1. **The server wait is the dominant cost, and this item does not remove it.** TTFB averages
   187 ms of a 259 ms load. What the item removes is staring at a frozen previous page while
   it happens, which is exactly what `loading.tsx` is for. The JS re-execution is real but
   second order on a fast machine with a warm V8 code cache; a colder machine pays more.
2. **These numbers understate production, and cannot be compared to it.** The database here is
   on the same machine. Production talks to Frankfurt, and every page spends 2 auth round trips
   plus 1 to 4 data waves before rendering. Production TTFB is strictly worse than 187 ms
   whatever the Vercel region turns out to be.
3. **The queue was empty.** Zero items, so these are best-case renders: no rows, no photos, no
   signed-URL calls. A real queue is heavier.
4. **A leader, not an admin.** The local stack seeds one staff account and it is a leader, so
   `/verses`, `/sermon-audio`, `/branches` and `/academy` were not measured. The measured set
   is the branch-leader daily path, which is the common case anyway.

**The `getClaims()` question is settled, and the answer removes work.** The local session token
decodes to `{"alg":"ES256","kid":"b81269f1-21d8-4f2e-b719-c2240a840d90"}`, and that kid is
exactly the one the local JWKS publishes, so `getClaims()` finds the key and verifies **locally
with no network call**. `proxy.ts:21-23` is telling the truth. Production publishes an ES256 key
of its own (`fffd4464-f169-4372-bdce-c0e2ce3f91ed`) by the same mechanism, so the HS256 fallback
almost certainly does not apply there either. **Consequence: prefetch is cheap, and slice 3
needs no `Next-Router-Prefetch` guard.** Strictly, the production token header itself is still
unverified; the cheap confirmation is one look at Project Settings, JWT Keys.

**Still open from slice 1:** the `agbc-dashboard` Vercel function region, which needs the
console. It changes nothing about what gets built, only how much reading 2 sees.

## 8. Verification this item owes

- `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm build` green on every slice. The local
  Supabase stack must be running: both Vitest projects load the same `globalSetup`.
- **Timings, not adjectives.** Slice 1's baseline re-run after slices 3, 4 and 5, on
  `next start`, recording hard versus soft navigation for the rail and the moderation chips.
  "Feels faster" is not the evidence this item is judged on.
- Screenshots of every visible change in both themes, diffed element by element against the
  frame, and every new skeleton against its own frame.
- A narrow window (`25` §5). The mockup's loading frames are drawn at `.win.narrow`, 900px.
- Keyboard pass plus `expectNoA11yViolations` on touched components, and a check that
  `aria-current="page"` survives the `<Link>` conversion.
- After slice 4, every route path in the build output matches the current one exactly.
- **Do not touch `.github/workflows/pr.yml` in any of these PRs.** It sits in all three
  `dorny/paths-filter` entries (`:48,:59,:62`), so editing it turns a dashboard-only change
  into a full-matrix run against the shared Actions minutes pool. A file move alone triggers
  only the `dashboard` job, which is correct and expected.
- **Merging is not shipping** (`21` §3): `agbc-dashboard` redeploys on every push to `main`.
  Nothing in this item touches `supabase/`, so no migration dispatch is owed. Confirm that at
  the end rather than assuming it.
