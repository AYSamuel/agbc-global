## The four decisions taken with Ayo before any SQL (2026-08-19)

1. **The service dedupe key carries the local start time.** `02` and the shipped
   `notifications.dedupe_key` comment say `service_reminder:<branch_id>:<service_date>`,
   and that key cannot keep its own promise: two services on one date at one branch share
   it (the evening one is swallowed), and a service moved from 11:00 to 18:00 on the same
   date is swallowed too, which is exactly the "rescheduled" case the rule names. The key
   is `service_reminder:<branch_id>:<YYYY-MM-DD>T<HH24:MI>`, exactly parallel to `02`'s own
   RSVP key which already embeds `starts_at_local`. `02` is corrected in slice 1's PR.
2. **Prayer cadence: day 1, day 3, day 7, then stop.** Hard cap 3. The clock is anchored to
   `committed_at`, never to the last send, so a nudge held back by quiet hours does not
   push the rest of the cadence out.
3. **Prayer nudges hold to 08:00-21:00 branch-local.** `15` asks for quiet hours and
   nothing implemented them. A prayer nudge is the one reminder with no natural clock (a
   service reminder is an hour before a service, an RSVP reminder the day before an event),
   so it is the one that needs the rule. Applies to prayer reminders only.
4. **The retention purge keeps OPEN reports.** An open report past 24 months is a process
   failure, not stale data, and deleting it destroys the evidence and the task together.
   Settled reports purge on schedule; open ones are counted and logged.

## Two rules this item follows that are worth stating once

- **The pref gate lives in SQL, in each job's batch query, on the column `15` names for
  that tier** (`service_reminders`, `prayer_reminders`; RSVP is transactional and has no
  gate). ADR 0016: the database decides who, the function delivers. `allowedByPrefs` in
  `_shared/pushChannels.ts` therefore is NOT called by these jobs; it stays W3.5's, for the
  fan-out. Two gates on one fact would be two owners, and they disagree today: the `prayer`
  channel routes to `prayer_activity` because one control writes both columns, while the
  tier `15` describes is gated by `prayer_reminders`.
- **Rows are written BEFORE the push, never after.** The unique index on
  `(profile_id, dedupe_key)` is the no-double-send guarantee (ADR 0022), so claiming the
  send is the insert. A push that then fails degrades to notification-centre-only, which is
  the degradation `15` already specifies for push being off; the run still pings FAILURE.
