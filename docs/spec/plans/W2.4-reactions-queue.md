# W2.4 · Reactions + offline queue: execution plan

Build blueprint for the item that makes the wedge respond. Behavioral truth is
`09-FEATURE-Family.md`; the queue contract is `01-ARCHITECTURE.md` §8; the counter and
forgery rules are `02-DATA-MODEL.md`. This doc adds sequencing, the decisions found while
planning (2026-07-27), and the two things that need Ayo's call before code. Delete once
W2.4 lands. Read `09` + `01` §8 + `02` first-hand in the build session, and read the
prayer frames in `design/mockups/entry-flow.html` (FAMILY PRAYER L1313, PRAYER-DETAIL
L1358 and L1378) first-hand before touching those screens.

## What is already done (do not rebuild)

The surprise of this plan: **the entire backend for both reactions already exists**,
landed with W1.5 and covered by pgTAP 008/009/010. W2.4 adds no table, no policy and no
trigger. Specifically, in `20260720220000_create_family_domain.sql`:

- `glory_reactions` and `prayer_intercessions` with `FORCE RLS`, the member policies
  (react / take back; commit / fulfil / withdraw), and `unique (prayer_id, profile_id)`.
- Forgery guards: both insert guards overwrite `profile_id` with `auth.uid()`, and refuse
  a target that is not published (`testimony_is_published` / `prayer_is_published`).
- The one-way state machine: `committed` → `prayed` only, `prayed_at` set by the trigger,
  and `committed_at` / `next_reminder_at` / `reminder_count` refused to clients outright,
  so a member cannot backdate a commitment or reschedule anyone's reminders.
- Server-maintained counters: AFTER INSERT/DELETE triggers move `glory_count`,
  `praying_count` and `prayed_count`, running as SECURITY DEFINER behind the
  transaction-local `agbc.counter_write` flag so the content guards can tell a counter
  write from a client trying to inflate its own number. Non-negative CHECKs underneath.

Also already in place on the client:

- `TestimonyCard`'s `GloryPill` and TESTIMONY-DETAIL's `.glorybig` render the count.
- `PrayerCard` already renders all THREE commitment states (`none` / `committed` /
  `prayed`) from a `commitment` prop, and PRAYER-DETAIL already has the "I will pray"
  button, the explain line and the gate. **Nothing supplies the prop yet**: every card
  renders `none` because the app has never read the member's own reactions.
- Gate + gate-return: `GateAction` already carries `glory` and `intercede`, and
  `replayGateAction` writes the Glory directly today (W2.2). W2.4 replaces that direct
  write with an enqueue, so one code path serves both the normal tap and the gate replay.
- i18n exists in all four languages: `iWillPray`, `iPrayed`, `youPrayed`, `prayingCount`,
  `prayedCount`, `willRemindYou`, `prayCommitExplain`, `gloryCount`.

So this item is a **frontend slice with a verification tail**, not a vertical slice. The
"Build BE" half of the usual shape is already merged.

## What is actually missing

1. **The member's own reaction state.** Nothing queries `glory_reactions` /
   `prayer_intercessions` for "what have I already done", so no card can render its
   selected state after a reload. Both tables have a members-read-their-own SELECT policy
   already, so this is a query, not a schema change.
2. **The offline write queue** (`01` §8), which does not exist in any form.
3. **The Glory burst** (`05` §Motion: small burst + count tick; under OS reduce-motion it
   degrades to a colour/fill change with the count announced via a live region).
4. **Wiring**: tap → optimistic UI → queue → replay → quiet reconciliation.

### 1. How does the app learn it is back online?

The queue's whole job is "replay on reconnect", and this app currently has **no
connectivity signal at all**: no `@react-native-community/netinfo`, no `expo-network`, and
TanStack Query's `onlineManager` is left at its default, which in React Native assumes
always-online. Three ways out:

| Option | Reconnect latency | Cost |
|---|---|---|
| **A. `@react-native-community/netinfo`** | immediate, event-driven | a NATIVE module: another EAS dev build before it can be tested on device, and the dev-client fence applies (guarded import, older clients degrade). It is the module TanStack documents for `onlineManager` in RN, and Expo ships it in their managed-workflow list |
| **B. No library** | seconds to a minute | replay on app foreground + after any successful query + a bounded retry timer. Zero native surface, ships on the current dev clients today. Reconnect while the app sits open on one screen is the weak case |
| **C. netinfo now, but behind the same guarded-require pattern** | immediate when present, option B's behaviour when absent | both code paths to maintain, but nothing blocks on the rebuild |

Recommendation: **C**. The queue's correctness must not depend on a native module, and B's
triggers are the honest fallback anyway; adding netinfo on top makes reconnect immediate
for everyone once the next dev build lands, without gating this work item on it.

### 2. Which entities does the queue cover on day one?

`01` §8 lists six: Glory toggle, prayer commit/fulfil, RSVP, attendance "I'm here",
plan-day complete, playback position. **Four of those belong to work items that do not
exist yet** (RSVP is W2.9, "I'm here" is W2.8, playback is W3.1, the plan is Phase 4).

Recommendation: build the queue as a **registry** with two handlers registered now (glory,
intercession) and a typed slot each later item fills in its own slice. The queue's shape,
persistence, eviction and replay driver are written once, here, and W2.8/W2.9/W3.1 add a
handler rather than a queue. `01` §8's list becomes the registry's TODO, not this slice's
scope. State that in the PR so the later items inherit it knowingly.

## Resolved decisions (2026-07-27)

1. **Desired end-state, not an op log** (`01` §8, non-negotiable). The queue is a map
   keyed by `(kind, entityId)` holding the state the user last chose. Tap-untap-tap
   collapses to one entry, so exactly one idempotent write replays per entity and ordering
   races cannot happen. This is what the Done criterion tests.
2. **Glory is a toggle; the prayer commitment is not.** `09` says "tap again to remove"
   for Glory, and the table has a DELETE policy for it. The two-step prayer is deliberately
   forward-only in the UI (`committed` → `prayed`, never back): `09`'s whole point is that
   a tap means real prayer. The DELETE policy on `prayer_intercessions` stays for account
   deletion, not for a withdraw button, and no frame offers one.
3. **Idempotent writes, matching what already exists.** Glory inserts go through
   `upsert(..., { ignoreDuplicates: true })`, which the counter trigger is already written
   around ("a skipped conflicting insert fires no trigger", `02`). The intercession commit
   is the same shape; the fulfil is an UPDATE the trigger refuses to repeat, and a refusal
   on replay is a success from the queue's point of view.
4. **Server state wins, quietly.** A rejected replay reconciles the UI without a toast:
   the member did something the server no longer allows (the post was removed, the prayer
   answered), and shouting about it helps nobody. Eviction is the exception, because
   eviction silently drops a promise: it reverts that entity's optimistic UI, per `01` §8.
5. **The queue is not the cache.** It persists to AsyncStorage under its own key, NOT
   through the TanStack persister (which is opt-in per query, `lib/queryMeta`), and it is
   cleared on sign-out. A queued write belongs to the member who made it.

## Slice 1: the queue (`feat/w2-4-offline-queue`)

No UI. A pure reducer plus a thin driver, which is the only way this gets tested properly.

- `src/lib/writeQueue/` : the reducer (`set`, `takeAll`, `evict`, `clear`), the persisted
  shape and its version, the handler registry, and the replay driver.
- Cap and eviction: a small fixed ceiling, oldest entity first, and eviction emits the
  reverted entity so the UI can put itself back.
- Triggers per the answer to question 1.
- Cleared on sign-out (hook into the existing auth store's sign-out path).
- Tests: tap-untap-tap replays as ONE write; a replay that fails with a server refusal
  drops the entry and reconciles; a transport failure keeps it; eviction reverts; a
  persisted queue from an older shape is discarded rather than hydrated.

## Slice 2: Glory (`feat/w2-4-glory`)

  W2.2 still passes with the queue underneath.
