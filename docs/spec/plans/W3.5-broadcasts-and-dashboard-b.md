# W3.5 · Broadcasts + Dashboard Phase B (slice plan)

Working plan for issue #175. **Delete this file when the item lands**; what it decided
belongs in `17`, `02`, `15`, `21` §5, the ADRs, and each migration's own header.

Position at start: `main` at 9a6a75d (PR #203, W3.4 complete and live on production).
`broadcasts` and `broadcast_deliveries` do not exist. `notifications.broadcast_id` exists
WITHOUT its foreign key, deliberately (`20260816120000`'s header: "W3.5 adds
`references public.broadcasts (id) on delete cascade` and nothing else").

## The four decisions taken with Ayo before any SQL (2026-08-19)

1. **A broadcast link may point at an in-app path or at agbcglobal.com, and nothing else.**
   `17` §2 asked for links to be "allowlisted/previewed" and never said what the allowlist
   held. A broadcast link is the one place a leader's typing becomes a tap target on hundreds
   of lock screens, which is exactly why `15`'s deep links are navigate-only. So: an
   expo-router path (validated against the app's own allowlist shape) or an https URL on
   `agbcglobal.com` or a subdomain. Anything else is refused at compose time, with the reason
   shown, and the leader's route to a third-party link is the WhatsApp copy, where a human is
   the gate.

2. **There is no daily send cap. EVERY broadcast is approved by an admin who is not its
   author.** This REPLACES `17` §2's "per-account daily send caps" and REWRITES `02`'s state
   machine, which gave branch scope no approval state at all. One rule, no exceptions by role
   or by scope: the approver must be an admin and must not be the author. The approval gate
   is the blast-radius control that the cap was reaching for, and it is a better one, because
   it bounds WHAT goes out rather than how often.

3. **No break-glass, deliberately, with a known cost.** Production has exactly two admin
   accounts. Either of them being unreachable stops all broadcasting, and a future
   single-admin period stops it entirely. Ayo chose that over a conditional self-approval
   rule, on the grounds that a rule with an exception is a rule people misremember. **This is
   the thing to revisit if it ever bites**, and `17` records it as a decision rather than an
   oversight.

4. **All five slices stay under W3.5**, as `25` defines the item, one PR per slice.

## What the approval rule changes, concretely

- **Both scopes** now run `draft` -> `pending_approval` -> `sending` -> `sent`, or
  -> `rejected`. `halted` and `failed` are unchanged.
- `approved_by` is set by the approval action and is `NULL` before it; the DB CHECK
  `approved_by is distinct from author_id` already specified in `02` now guards every
  broadcast rather than only ministry ones.
- **The approver being an ADMIN is not expressible as a CHECK** (the role lives on
  `profiles`), so it is enforced in the approve function via `caller_is_admin_live()`, which
  is the ADR 0015 rule: read authority from the live table, never from a JWT claim.
- An author edit while `pending_approval` returns the row to `draft` and clears
  `approved_by`, by trigger. What the approver reviewed is what sends.
- `02` §broadcasts and `17` §2 are corrected in slice 1's PR.

## No `privileged_actions` row for an approval, and why

ADR 0015 puts privileged actions in a ledger written by a trigger. This one does not go
there, and the reason is the ledger's shape: `privileged_actions` is profile-oriented
(`actor_id`, `target_id` both referencing `profiles`) and a broadcast approval has no profile
target. The broadcast row IS its own audit record: it carries `author_id`, `approved_by`,
`sent_at` and `review_note`, and its content columns are immutable from `sending` onward, so
"who approved what wording" is answerable from the row itself. The ADR's real requirement,
that the record cannot be forgotten by a caller, is met by the trigger that stamps it.

## Slices

### Slice 1 · the broadcast domain (BE)

- `broadcasts` + `broadcast_deliveries` migrations per `02`, with the state machine enforced
  by trigger and CHECK, the four-eyes CHECK, the edit-during-approval reset, and the
  approve/reject/halt functions (admin-only, live-table authority).
- `notifications.broadcast_id` finally gets its FK.
- Recipient-count function shared by the confirmation screen and the fan-out, so the number
  a leader is shown and the number that receives are one definition.
- RLS: zero client policies, service-role only (`02`'s matrix row).
- pgTAP: every state transition including the refused ones, self-approval, edit-during-
  approval, immutability from `sending`, and the recipient count against prefs and blocks.

### Slice 2 · the fan-out (BE)

- `broadcast-fanout` edge function: chunked (100 per Expo call), cursor-resumable via
  `broadcast_deliveries`, halt-aware between chunks, deduped by `unique(profile_id,
  broadcast_id)`, respecting `notification_prefs` and blocks in either direction.
- Broadcasts carry PRE-RENDERED `title`/`body` per recipient language rather than a template
  key, so this is a second path through the seam rather than a reuse of `deliver_notifications`
  as it stands. Decide in the slice whether the seam grows a pre-rendered mode or the fan-out
  writes its own rows; the dedupe index is the guarantee either way.
- The `21` §6.4 alerts: >10% delivery failure, and a broadcast stuck in `sending` past 15
  minutes with zero failures.

### Slice 3 · dashboard broadcasts (FE)

Compose (scope, locale bodies, link allowlist + preview, "Copy for WhatsApp"), the
confirmation screen (exact recipient count, fully rendered body, expanded link), the approval
queue, halt, history with per-channel outcomes.

### Slice 4 · events CRUD + auto-notifications

Dashboard events module; cancellation, reschedule and reinstate auto-notify every
non-cancelled RSVP (`11`).

### Slice 5 · branches + the archive flow

Branch add/edit; archive blocked until leaders are reassigned or demoted, then stopping
reminders and broadcasts, hiding the branch from pickers and the map, escalating residual
pending moderation to admins, and prompting its members to choose a new home branch.
