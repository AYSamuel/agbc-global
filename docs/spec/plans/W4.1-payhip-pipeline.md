## 1. Why this item is not what its name said

Two of the three things `25` asked W4.1 to build are done or were deliberately deleted, and
one of the things it asked for cannot be built at all. All three were found by reading the
refs before starting, and they are recorded here so the next session does not rediscover
them.

### The Payhip API `14`'s trust model was designed around does not exist

`14` says a grant happens only "after server-side confirmation against Payhip's API, keyed
by transaction id", and `21` §5 schedules a daily job that "pulls the last 7 days of
transactions from the Payhip API". Checked against Payhip's own documentation on 2026-09-01:
**the public API covers coupons and licence keys only.** Payhip's own words: "At the moment
we only have support for interacting with the Coupon and License Key resources, but more
will be added in future." There is no transaction, sale, order or customer endpoint in
either v1 or v2.

So three promises cannot be kept as written: the confirmer, the refund confirmation ("revoke
ONLY after the API confirms refund status for that `source_ref`"), and the reconciliation
job for silently dropped webhooks.

What `14` got right on 2026-07-12 and is still true: the webhook signature is
`hash('sha256', $apiKey)`, a constant across every event, with no payload HMAC and no
timestamp. It authenticates nothing about the payload and is replayable. Payhip still
documents it in exactly those terms.

### The "email verification" half is done or deleted

- **Resend custom SMTP** (`24` §1 row 12) landed at Track P Phase 2 on 2026-08-19 and is
  verified: `18`'s checklist line is ticked, DKIM byte-compared before cutover, and
  `mailer_otp_exp` / `smtp_max_frequency` set to match the app's resend countdown.
- **The dedicated email-verification OTP was struck on 2026-07-18.** `03` §Security: "The
  identity email is verified by definition, so the Payhip restore-purchase flow (`14`) needs
  no separate email-verification step." `14` says the same under its own heading.

What remains under that half of the name is the restore-purchase claim flow, so the item is
renamed **W4.1 · Payhip pipeline + restore purchase** in `25`.

## 2. What the website does, and why it needs nothing from us

Checked first-hand on 2026-09-01, because "the website's bookstore is manual" invites the
assumption that this item automates it. It does not, and it should not.

`Desktop/agbc`'s store is `src/pages/store.astro` over `src/content/books/*.json`. The whole
catalogue today is ONE book: the 1st edition Word Devotional, £10, PDF, Payhip id `5cLzF`.
`BookCard.astro` renders a plain link to `https://payhip.com/b/5cLzF`, loads no Payhip
script, and its own comment says "the link IS the checkout path".

**That is a shop window, and manual is the correct design for one.** A buyer clicks through,
Payhip takes the money and emails them the PDF, and the website never learns a sale happened
because it has no reason to: the buyer already has the file.

**The app is a different problem entirely, and it is the only reason any of this exists.** On
the website, "I paid" and "I can read it" are the same moment. In the app they are two facts
that have never met: somebody pays on Payhip's site, in a browser, under whatever address
they typed at checkout, and then separately opens an app where they are signed in as
themselves. Nothing connects those two unless we build the connection. Everything below is
that connection.

Note also: this one book is the devotional, so it is simultaneously W4.4's reading plan
(ADR 0008, `reading_plans.book_id`). The entitlement that unlocks the book unlocks the plan.

## 3. The trust model: licence keys, and the credentials it needs

Decided with Ayo on 2026-09-01, and it replaces `14`'s transaction lookup.

Payhip's one server-side proof of purchase is licence-key verification:

| | v1 | v2 |
|---|---|---|
| endpoint | `GET https://payhip.com/api/v1/license/verify` | `GET https://payhip.com/api/v2/license/verify` |
| auth | `payhip-api-key` (the ACCOUNT key) | `product-secret-key` (per product, on the product's edit page) |
| takes | `product_link` + `license_key` | `license_key` |
| returns | `enabled`, `uses`, `buyer_email`, `product_link`, `date`, `license_key` | same |

And critically: **Payhip automatically disables a licence key when its transaction is
refunded.** So `enabled` is a refund signal we can read on demand, which is most of what the
missing transactions endpoint was for.

### Use v2, and never hold the account API key

Payhip has **one API key per account, with no scopes and no read-only mode** (checked
2026-09-01; the only control offered is rolling it). That key authenticates
`POST /api/v2/coupons`, so it can mint discount coupons on the church's store, up to and
including free ones. It is a live financial capability on the lead pastor's own account.

v2's `product-secret-key` is the scoped credential instead: one per book, and it can only do
licence operations for that book. **So the account key is never requested and never stored.**

### Where the per-product secrets live

**Supabase Vault, keyed by the book's Payhip permalink**, read at call time by the confirmer,
exactly the way `jobs.invoke_edge_function` reads `project_url` and `secret_key` (ADR 0016).
Not a column on `books`: a credential does not belong in a table an admin can read, even a
narrowly granted one. Not a function secret per book either: that does not scale past two
titles and puts a deploy between the church and a new book.

Consequence to design for: an environment whose vault lacks a book's secret **cannot confirm
that book's sales**, and that must be a loud failure (an alert plus a FAILURE ping, per
ADR 0016's rule) rather than a silent skip, because the silent version is a buyer who paid
and never got their book.

### The webhook needs a constant, not a key

The receiver's only authentication is comparing the payload's `signature` against
`sha256(accountApiKey)`. Since sha256 is one-way, **Ayo computes that digest himself and
hands over only the 64-character result.** The account key never leaves the pastor's Payhip
account, and what we store can verify a webhook and do nothing else.

### The three-item ask (replaces `24` §1 row 13's "API key + webhook config")

1. **The webhook signature constant.** `sha256` of the account API key, computed by Ayo.
2. **One `product-secret-key` per book**, from each product's own edit page.
3. **A test product with licence keys switched on**, so a real webhook payload and a real
   licence verify can be seen before the confirmer is written against documentation alone.

## 4. The decision Ayo owns, and the open questions the test product answers

**Payhip offers auto-generated OR pre-generated licence keys per product, never both.** This
is the choice, and it decides whether the AUTOMATIC path can be confirmed at all.

**Auto-generated.** Payhip mints a unique key per sale and gives it to the buyer. We never
see it: the `paid` webhook payload (`id`, `email`, `currency`, `price`, `items[]`,
`payment_type`, `stripe_fee`, `payhip_fee`, `is_gift`, `date`, `type`, `signature`) carries no
licence key field. So the automatic grant cannot be confirmed, and licence verification
serves only the restore path and refunds.

**Pre-generated (RECOMMENDED).** We upload a pool of keys we generated, and Payhip assigns
one per sale. Because we know every key in the pool, a periodic sweep can verify them and
learn which have been sold, to whom, and whether they are still enabled. That single sweep
rebuilds **all three** things the missing transactions API was supposed to give us:
confirmed sales, refund detection, and recovery of webhooks that never arrived.

Its cost is one real operational fuse: **the pool is finite.** Run out and buyers stop
getting keys. So it needs a top-up job and a low-water alarm, and the alarm has to be derived
from our own count of assigned keys against the pool size, because there is no endpoint that
reports how many Payhip has left.

**What buyers see changes either way**: they start receiving a licence key with their
purchase. That is a product decision for Ayo, not a build decision.

Open questions, all answerable in about ten minutes with the test product:

1. Does **v1** still work? If it does, one account key serves every product and there are no
   per-product secrets to manage; the trade is the unscoped key, which is why v2 is the
   default here rather than an obvious loss.
2. What does verify return for a key that is **in the pool but not yet sold**? If it errors
   rather than answering "unassigned", the sweep still works (either answer means "no sale to
   confirm"), so this is a smaller risk than it first looks, but it shapes the code.
3. Which webhook field is the **stable product identifier**: `items[].product_id`,
   `product_permalink`, or `product_key`? `books.payhip_product_id` is the join key between an
   arriving sale and our catalogue and is currently a guess. The website's `payhipId` (`5cLzF`)
   is the permalink, so `books.payhip_product_link` is very likely already right.
4. Does the refund webhook carry the sale's `id` unchanged? Slice 2 assumed yes and made the
   inbox unique on `(event_id, event_type)` because of it.

### S1 · The trust model, settled against the real account

**The next thing to run, and the only one blocked.** Needs the three-item ask from §3. Test
the four open questions in §4, take the auto-vs-pre-generated decision with Ayo, then write
**ADR 0025** and amend `14` (the flow diagram, "What the API confirmation checks",

**If pre-generated turns out unworkable,** the fallback is the webhook treated as a shared
bearer secret (constant-time compare of the signature constant, secret function URL, every
grant visible and revocable in the dashboard), with licence verification kept for refunds and
restore only. That reverses `14`'s stated position, so it is Ayo's call and not a session
decision, and it gets recorded as a knowingly accepted risk rather than an oversight.

### S3 · The inbox

- `payhip-webhook` receiver: `verify_jwt = false`, constant-time compare against the stored
  signature constant, insert raw into `payhip_events` on the `(event_id, event_type)` unique
  so replays no-op, and **always 200**, so the response never reveals whether we already knew
  the id. Its `[functions.payhip-webhook]` block goes in `config.toml` in the same commit: a
  function without one is a job that no-ops silently in BOTH environments (the W3.6 lesson).
- `payhip-inbox` job, every 5 minutes, on ADR 0016's mechanism: `cron.schedule` calling
  `jobs.invoke_edge_function`, a lease taken and released, work derived from live state, and
  a healthchecks.io ping that reports FAILURE when it could not deliver
  (`HEALTHCHECK_URL_PAYHIP_INBOX`).
- Confirm per S1, then grant into `entitlements` (unique `source_ref`) or file into
  `unmatched_purchases` when no profile has that address yet.
- Refunds revoke rather than delete: set `revoked_at` + `revoked_reason`, which closes both
  LIBRARY and the `book-files` mint policy.
- Tests: `deno test` for the pure logic, plus `21` §4's integration pair through
  `supabase functions serve`: the same fixture replayed twice grants exactly once, and a
  forged refund does not revoke.

### S4 · The drain and the sweep

- A trigger on a profile appearing (or an auth email change, `03`) that grants matching
  `unmatched_purchases` rows through the same confirmed path, setting `resolved_at` and
  `resolved_profile_id`.
- The job's own re-sweep as the safety net, per `14`.
- The licence-pool sweep from §4, if pre-generated wins: confirmed sales, refunds, and
  dropped-webhook recovery in one pass, plus the low-water alarm on the pool.
- If S1 lands on the fallback instead, reconciliation is **impossible**, and that gets
  recorded as an accepted gap in `14` and `21` §5 with the restore path named as the human
  net, rather than left implied.

### S5 · Restore purchase

Edge function only; the screen is W4.2's.

- Grants against the profile's identity email read **server-side** from the session, never
  from the request body, or against the proof S1 settles on (a licence key, or a Payhip order
  id checked against our own `payhip_events` inbox, which needs no Payhip call at all).
- **Uniform response either way**: "if a matching purchase exists, it will be added". No
  enumeration signal, whether or not anything matched.
- Rate-limited per account and per IP.

### S6 · `purchase.added` gets its producer

The last orphaned notification template; `18`'s launch checklist already assigns it here.

- A fifth arm on `activity_notice_batch` scanning `entitlements.granted_at`, with its index
  (already built in slice 2: `entitlements_granted_at_idx`), filtered to `revoked_at is null`.
- Mapping in `activity-notices/core.ts`: type `purchase` (already routed to the transactional
  channel with no pref key in `_shared/pushChannels.ts`, and already in the
  `notifications_type_known` CHECK), template `purchase.added`, deep link `/library` (already
  on the app's allowlist in `features/notifications/deepLinks.ts`).
- The template's body is "{title} is ready to read", so **this arm carries the book title**,

  of `core.ts`: a book the church sells is not the special-category content `15` and `20`

- A job arm rather than a write inside the granter, for every reason W3.6 slice 2 and #164
  recorded: ADR 0016 (a trigger-fired send fails silently), `21` §5's no-outbox rule, and
  ADR 0022 (the insert IS the claim on a send).

## 6. Decisions already taken (S2), for anyone reading the migration

1. **`books.file_url` / `cover_url` are `file_path` / `cover_path`.** What belongs in a row is
   the PATH: a signed URL expires and a public one pins the project host into every row.
2. **A third bucket, `book-covers`,** which `02` §Storage did not list. A cover has nowhere
   else to live, and hotlinking Payhip's CDN would put a third party's URL on every card in a
   guest-first grid. `sermon-artwork`'s posture exactly.
3. **`book-files` is minted through an RLS SELECT policy, not an edge function.** W2.3
   overturned that same wording for `testimony-photos`: the policy gives the identical
   guarantee with no extra service on the read path. The policy joins `books` to
   `entitlements` on `revoked_at is null`, which is how a refund closes READER too.
4. **`entitlements` revokes rather than deletes.** `14` promises a re-purchase restores place
   and progress, and a deleted row cannot say what was taken back or why.
5. **The inbox is unique on `(event_id, event_type)`.** Payhip's refund webhook carries the
   ORIGINAL order id, so a single-column unique would swallow every refund as a replay.
6. **`reading_state` keeps `02`'s `PK(profile_id, book_id)`,** with `profile_id` defaulting to
   `auth.uid()` and excluded from the INSERT grant. **The PostgREST upsert road must be driven
   for real before W4.2 calls that screen done**: a privilege proven in pgTAP is not yet proven
   through PostgREST (the W3.1 slice 4 lesson).
7. **Admins write the catalogue through RLS and grants, not a service-role route,** and there
   is no DELETE for anyone: removing a title from sale is clearing `published_at`, which keeps
   it in the Library of everybody who bought it.

## 7. Loose ends noted but not owned by this item

- **`devotional_purchased_matched`** (`packages/shared/src/analytics/events.ts`) is marked
  `deferred`, owner "Phase 4 · entitlement pipeline". It cannot fire from the server: analytics
  identity is the DEVICE and only the device (ADR 0020), and a server-side grant has no device.
  So it fires from the app when a Library refetch discovers a newly matched book, which makes
  it **W4.2's**, not this item's. Decide it there.
- **W4.2's store grid has no covers until W4.4** builds the dashboard's upload, since slice 2
  seeded books with null paths deliberately (a seed runs as the service role, so the path guard
  waives itself and a seeded path would be a dangling reference nothing refuses). Either seed
  dev cover objects with a script, the way `db:reset` does for sermon audio and artwork, or
  accept the branded placeholder until W4.4.
