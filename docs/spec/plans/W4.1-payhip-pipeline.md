## Why this item is not what its name says

Two of the three things `25` asked W4.1 to build are already done or were deliberately
deleted, and one of the things it asked for cannot be built at all. All three were found by
reading the refs before starting, and they are recorded here so the next session does not
rediscover them.

### 1. Payhip has no transaction API, and `14`'s trust model was designed around one

`14` says a grant happens only "after server-side confirmation against Payhip's API, keyed
by transaction id", and `21` §5 schedules a daily job that "pulls the last 7 days of
transactions from the Payhip API". Checked against Payhip's own documentation on
2026-09-01: **the public API covers coupons and licence keys only.** Payhip's own words:
"At the moment we only have support for interacting with the Coupon and License Key
resources, but more will be added in future." There is no transaction, sale, order or
customer endpoint in either v1 or v2.

So three promises cannot be kept as written: the confirmer, the refund confirmation
("revoke ONLY after the API confirms refund status for that `source_ref`"), and the
reconciliation job for silently dropped webhooks.

What `14` got right on 2026-07-12 and is still true: the webhook signature is
`hash('sha256', $apiKey)`, a constant across every event, with no payload HMAC and no
timestamp. It authenticates nothing about the payload and is replayable. Payhip still
documents it in exactly those terms.

**The decision taken with Ayo on 2026-09-01: licence keys become the proof.** Payhip's one
server-side verification is `/api/v1/license/verify` (`payhip-api-key` header, with
`product_link` + `license_key`) or `/api/v2/license/verify` (a per-product
`product-secret-key` header), returning `enabled`, `uses`, `buyer_email`, `product_link`,
`date`. And Payhip "automatically disable[s] the license key if the transaction has been
refunded". That is the same shape `14` wanted from a transaction lookup (product, buyer
email, refund status), keyed on a licence key instead of a transaction id, and it gives
refund detection and a reconciliation sweep for free.

**Unverified until the key handoff (`24` §1 row 13), and S1 exists to settle it:**

- Does v1 still work? It needs only the account-level API key plus the product permalink,
  where v2 needs a per-product secret. That difference decides whether a per-book credential
  has to live in Vault, which is the difference between a column and a secrets problem.
- Where does the buyer's key come from on the AUTOMATIC path? The `paid` webhook payload
  (`id`, `email`, `currency`, `price`, `items[]`, `payment_type`, `date`, `type`,
  `signature`) carries no licence key. So either we upload PRE-GENERATED keys and verify
  each one to learn which buyer it went to, or the automatic path cannot be confirmed at all
  and only the restore path can. This is THE open question and it is answerable in ten
  minutes with a real key.
- What does verify return for a key that exists but has not been sold yet?
- Auto-generated and pre-generated are mutually exclusive per product (Payhip's own
  constraint), so this choice is per book and cannot be hedged.

**If the pre-generated route does not work,** the fallback is the webhook treated as a
shared bearer secret (constant-time compare of the signature constant, secret function URL,
every grant visible and revocable in the dashboard), recorded as a knowingly accepted risk
rather than an oversight. That reverses `14`'s stated position and therefore needs Ayo, not
a session decision.

### 2. The "email verification" half is done or deleted

- **Resend custom SMTP** (`24` §1 row 12) landed at Track P Phase 2 on 2026-08-19 and is
  verified: `18`'s checklist line is ticked, DKIM byte-compared before cutover, `mailer_otp_exp`
  and `smtp_max_frequency` set to match the app's resend countdown.
- **The dedicated email-verification OTP was struck on 2026-07-18.** `03` §Security: "The
  identity email is verified by definition, so the Payhip restore-purchase flow (`14`) needs
  no separate email-verification step." `14` says the same under its own heading.

What actually remains under that half of the name is the restore-purchase claim flow, so
the item is renamed **W4.1 · Payhip pipeline + restore purchase** in `25`.

## The slices

**S1 · The trust model, decided and written down.** Needs the Payhip key handoff and a test
product. Test the licence endpoints against the real account, take the decision, then ADR
0025 plus amendments to `14` (trust model, drain, reconciliation, restore), `21` §5 (both
Payhip job rows), `02` where the schema shifts, `25` (rename + corrected build line), `17`
§4 (the Library merge) and `18` (tick the stale line). Docs only.

**S2 · The shelf.** The five tables, both buckets, grants, RLS, the retention extension,
seeds, pgTAP. Decision-independent apart from two nullable columns that S1 confirms.

**S3 · The inbox.** `payhip-webhook` receiver (raw insert only, uniform 200, its
`[functions.payhip-webhook]` block in `config.toml`) and the 5-minute `payhip-inbox` job on
ADR 0016's mechanism: lease, live-state derivation, healthcheck with a FAILURE ping. Grant,
unmatched and refund revocation per S1. `deno test` plus `21` §4's integration pair: the
same fixture replayed twice grants once, a forged refund does not revoke.

**S4 · The drain and the sweep.** The trigger that grants when a profile with a matching
email appears, the job's re-sweep as the safety net, and whatever reconciliation S1's
decision permits. If it permits none, that is recorded as an accepted gap with the restore
path named as the human net, not left implied.

**S5 · Restore purchase.** Edge function only: identity email read server-side (never
client-supplied), or the proof S1 settles on; uniform responses either way; rate-limited per
account and per IP. No screen until W4.2.

**S6 · `purchase.added` gets its producer.** Fifth arm on `activity_notice_batch` scanning
`entitlements.granted_at`, its index, the mapping in `activity-notices/core.ts`, deep link
`/library` (already on the app's allowlist). Mutation-checked on both sides.

**S7 · The unmatched-purchases queue** in the dashboard, lighting the Library rail row.
In W4.1 rather than W4.4 because a pipeline nobody can look into cannot be operated, and
`17` §4 asks for this queue to be worked weekly.

## Decisions taken in S2 (the ones that depart from `02`'s sketch)

1. **`books.file_url` and `cover_url` become `file_path` and `cover_path`.** The W2.3 and
   W3.1 rule: what belongs in a row is the PATH, and calling a column a URL invites somebody
   to store one. A signed URL expires; a public URL pins the project host into every row.
2. **A third public-read bucket, `book-covers`.** `02` §Storage lists only `book-files`, and
   a cover has nowhere else to live: hotlinking Payhip's CDN would put a third party's URL
   on every card in a guest-first grid. Its posture is `sermon-artwork`'s exactly, and for
   the same argument (the cover is the advertisement, not the asset).
3. **`book-files` is minted through an RLS SELECT policy, not an edge function.** `14` and
   `25` W4.2 both say "per-request edge function"; W2.3 overturned that same wording for
   `testimony-photos` with a reason that transfers wholesale: the policy gives the identical
   guarantee with no extra service on the read path and one less place to re-implement the
   rule wrongly. Proposed to Ayo with this slice.
4. **`entitlements` gains `revoked_at` + `revoked_reason` instead of being deleted on
   refund.** `02` sketches neither. Deleting loses the record of what was taken back and
   why, and `14` promises a re-purchase restores place and progress, which needs the row's
   history to still be there.
5. **The inbox is unique on `(event_id, event_type)`, not on `event_id` alone.** Payhip's
   refund webhook carries the ORIGINAL order id, so a refund and its sale share an id and a
   single-column unique would silently swallow every refund as a replay. `14` says "unique
   event id: replays no-op"; this is what that has to mean in practice.
6. **`reading_state` keeps `02`'s `PK(profile_id, book_id)`,** with `profile_id` defaulting
   to `auth.uid()` and excluded from the INSERT grant (the W3.1 slice 4 rule: on a
   member-owned table with nothing else to force, identity is not an input). The PostgREST
   upsert road must be driven for real before W4.2 calls the screen done; a privilege proven
   in pgTAP is not yet proven through PostgREST.
