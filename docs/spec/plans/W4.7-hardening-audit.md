# W4.7 · Hardening audit: states, a11y, performance, tablet

The last engineering item before the MVP goes to a store. `25` sizes it as one session; the
survey below says it is five or six, because three of its clauses turned out to describe work
that has never been done rather than work that needs checking.

Refs: `18` Phase 4 + launch checklist, `05` (accessibility contract, tablet rules, contrast
rule), `04` (four states, no dead ends), `21` §4 (the manual matrix). Sequence agreed with Ayo
on 2026-09-02: **W4.7, then W4.6, then W4.8**, so that hardening can still move a string and
the translation freeze is the last word on copy.

**Delete this file when W4.7 lands.** What it decides belongs in `05`, `18` and the tokens.

## What the survey found (2026-09-02, before any code)

Baseline: working tree clean on `main` at `c9bd98d`, `pnpm typecheck` green across all three
packages, `pnpm test` green at 893 mobile + 339 dashboard.

### 1. Three More rows open a "coming soon" screen

`app/store.tsx`, `app/library.tsx` and `app/plan.tsx` are `StubScreen`s. Their work items are
W4.2 (Store + Library, which needs W4.1's pipeline, parked by Ayo on 2026-09-01) and W4.4
(the devotional plan). `18`'s own MVP definition already defers both: "ship ... Defer
Store/Library (and with it the paid devotional plan)". Nothing had removed the doors.

App Store guideline 2.1 rejects placeholder content, so this is the likeliest cause of a
re-submission cycle in W4.8, and it is a two-file fix.

### 2. Tablet layouts do not exist

`05` decided on 2026-07-12 that v1 ships real tablet layouts, "not just a capped column", and
the mockup carries nine tablet frames. The app has `Screen`'s `capped` width class and nothing
else: there is no breakpoint hook, no `isTablet`, and no master-detail anywhere in
`apps/mobile`. A tablet today gets a phone layout centred at 680px.

Ayo's decision (2026-09-02): **build the six in-scope layouts.** STORE and READER are out with
their features.

### 3. No list in the app is virtualized

There is no `FlatList`, `FlashList` or `SectionList` in `apps/mobile`. Every feed, result list
and notification centre is a `ScrollView` with `.map()`. **The risk is bounded rather than
unbounded**, because the Family feed caps at `FEED_LIMIT = 50` with no pagination, so nothing
here grows without limit. What it costs is measurable on a low-end device: fifty testimony
cards, several carrying remote photos, all mounted at once, on the screen a member sees most.

Virtualization has to land BEFORE the tablet layouts, not after: a two-pane layout puts the
list inside a pane, and a `FlatList` cannot be nested in a same-axis `ScrollView`, so doing it
in the other order means building each list twice.

### 4. The contrast finding is bigger than `25` recorded, and it is not only dark

`25`'s W4.7 entry carries one measured finding from W3.3: dark hairlines at ~1.43:1. Computing
every token pair against WCAG (values from `packages/shared/src/theme/index.ts`) says the
boundary problem is **both themes**, and that there are **text failures in light mode nobody
had measured**:

| Pair | Light | Dark | Rule |
|---|---|---|---|
| `cardline` vs `card` | **1.31:1** | **1.25:1** | 1.4.11 non-text, needs 3:1 |
| `cardline` vs `bg` | **1.24:1** | **1.42:1** | 1.4.11 |
| `bandline` vs `band` | n/a (transparent) | **1.42:1** | 1.4.11, the W3.3 finding |
| `muted` on `bg` / `card` / `alt` | **3.72 / 3.94 / 3.35** | 5.02 / **4.41** / 4.62 | 1.4.3, needs 4.5:1 for body |
| `blue` on `bg` | **4.29:1** | 6.64:1 | 1.4.3; this is the "See all" link at 12.5px |
| `eye` and `count` on `bg` / `card` | **3.06 / 3.24** | 12.53 / 11.00 | 1.4.3 |

Everything else passes, several comfortably. Note what this vindicates: `05`'s existing rule
that gold never carries text on light, and its deliberate lightening of `blue` in dark, are
both confirmed by the numbers. The light-mode `muted`, `blue`-on-page and `goldDeep` values
are the ones that were never checked.

**These are mockup values.** The repo convention is that the mockup wins on look and `05` gets
synced in the same change, so the corrected values are composed in `entry-flow.html` and
approved by Ayo BEFORE the tokens move.

### 5. Orientation is locked portrait app-wide

`app.config.js` sets `orientation: 'portrait'`. `05` says "player and reader support landscape
on all devices". The reader is deferred with W4.3, so this is the sermon player.

### 6. Two findings that belong to W4.8, recorded here because the survey found them

- **Neither `assetlinks.json` nor `apple-app-site-association` exists on the church website.**
  `app.config.js` declares `autoVerify` App Links and `associatedDomains` for both, and both
  halves are missing, so Android falls back to the disambiguation dialog and iOS declines the
  link entirely. The `agbcglobal://` scheme still works, which is why W3.6 could verify all
  four deep-link destinations on the device without this surfacing. Android's half needs the
  Play App Signing SHA-256 (a console lookup, and NOT the upload key, per the note already in
  `app.config.js`) and a PR against `Desktop/agbc`.
- **`APP_STORE_URL` is still a search URL**, with its own TODO in `src/lib/links.ts`. It waits
  on the App Store Connect numeric id, which is iOS, which is deferred.

### 7. iOS is out of scope for this item

Decided with Ayo 2026-09-02: **Android-first launch, iOS as a follow-on.** There is no iPhone
and no APNs key in the project, so `21` §4's "current iPhone" column of the manual matrix
cannot be executed, and it is deferred with the platform rather than waived. Everything in
W4.7 targets the real low-end Android.

### S2 · Contrast, in the mockup first · DONE (2026-09-02)

**The finding grew twice while being fixed, both times because a number was computed rather
than looked at.**

**First: one token was doing two jobs.** `cardline` drew the decorative hairline round a card
AND the border of every text field, OTP box, checkbox, unselected radio and chip, and outline
button, across 66 usages. It was also the OFF fill of a switch (`on ? green : cardline`), so
the whole difference between a switch's two states rested on a colour at 1.31:1 against the
card behind it. WCAG 1.4.11's 3:1 applies to the second group and is arguable for the first,
which is why `25`'s expected whole-palette re-tone was not the only option. Decided with Ayo:
**split the token.** `controlline` is new (light `#8c877d`, dark `#646b74`, measured to 3:1
against `bg`, `card` AND `alt`); `cardline` keeps its delicate hairline and its exemption is
now asserted rather than assumed. Twelve sites in the app moved, plus 27 in the dashboard,
which had conflated exactly the same two jobs in Tailwind classes.

**Second: writing the test found two more failures than the survey had.**
- Light `blue` clears 4.5 on the page and on a card but sits at **4.17:1 on `alt`**, which is
  the pressed-row background. The original solve had never included that surface. Re-solved
  against all three: `#2963d4`.
- The daily verse card's eyebrow was **2.68:1 on the darker end of its own gradient**, the
  worst text contrast in the app, on the surface Home leads with. It failed even the 3:1
  large-text bar, and it is 10.5px. `verseCard.eyebrow` `#b98600` to `#866100`.

Final values, each the same hue moved until it clears its threshold on the WORST surface it
sits on, with headroom rather than knife-edge: light `muted` `#716857` (4.66), light `blue`
`#2963d4` (4.65), light `eye`/`count` `#896300` (4.63), dark `muted` `#808a9c` (4.65),
`verseCard.eyebrow` `#866100` (4.65).

**The order was mockup, then tokens, then `05`,** per the repo convention. Rendered in Chrome
both themes and diffed against the pre-change render. **The first comparison harness was
wrong and had to be thrown away:** it put both versions on ONE page sharing the NEW stylesheet
and only swapped the variable VALUES, so the `--ctlline` rules applied to the "before" column
too and every border difference it showed was an artefact. Corrected by rendering each version
with its own stylesheet. Same lesson as the sweep in §3 below: an instrument that cannot show
a difference is not evidence of one.

`apps/mobile/src/theme/__tests__/contrast.test.ts` is the guard, 57 cases, one per pair so a
failure names the surface (which matters: `muted` passed on the page and failed on a card).
Mutation-checked by restoring three old values: exactly the eight expected pairs went red.

**A structural finding the sweep turned up on the way.** Three controls are drawn INLINE in
screens rather than composed from the primitives: Contact's `inputStyle`, the delete-account
confirmation field, and AUTH-3's `pickrowStyle`. They were only found because each had to be
classified by hand, and they are the reason the split is 16 sites rather than 13. The frontend
standard is explicit that a reusable widget never lives privately inside one screen, since the
next screen copies the first. Not refactored here, because retyping three form controls is not
a contrast fix and would hide the token change in unrelated diff. **Owed to S5**, where the
a11y sweep touches every form anyway.

**Two contrast questions this slice deliberately did NOT answer, both owed to S5** because
both need a composited measurement on a device rather than a token one:
- **Avatar initials** are 13px bold white on the branch gradient, whose lightest stop
  (`palette.goldDeep`) gives **3.24:1**. They repeat the author's name printed beside them, so
  they may well be decorative, but nothing has decided that on the record.
- **The gold-tinted badges** (`.pill.review`, `.quotemark`, `.tag2.global`, the NC glory disc)
  put `#b98600` on a translucent wash, so their true background depends on the card underneath
  and on the theme.

### S3 · Virtualization and the performance pass · IN PROGRESS (2026-09-02)

**`ListScreen`, a primitive rather than a `FlatList` per screen.** The chrome is the part
that is easy to get subtly wrong: the top inset plus `screenTop` that reproduces the
mockup's frame-top-to-title geometry, the bottom safe-area inset, the capped measure, and a
refresh control that spins only for a real pull. Seven screens hand-rolling that is seven
chances to differ, so it imports `Screen`'s geometry rather than copying it, and the
frontend standard says a reusable widget belongs in the library anyway.

**Converted, because these can actually grow:** the Family feed (both tabs), the
notification centre, MY-LIST and MY-POSTS. Notifications was the least defensible of all as
a `ScrollView`: it is the one list that genuinely paginates, so "show older" appended a page
each time and nothing ever unmounted.

**NOT converted, deliberately, and this is a judgement rather than an omission:**
- **Branches** renders four rows, bounded by how many branches the church has. Virtualizing
  it would add indirection and buy nothing.
- **Events** shows upcoming events only, and the same argument holds at its size.
- **WATCH-SEARCH** is the interesting one. Its results are server-capped at 30 to 50
  `SermonRow`s, which is light, and converting it would put a live `TextInput` inside a
  virtualized header. `ListHeaderComponent` given an inline element can remount as the list
  re-renders, which drops keyboard focus mid-typing: a real regression traded for no
  measurable gain. It stays a `ScrollView` until it paginates.

None of the four converted screens has an interactive header beyond `AppHeader`, so none of
them is exposed to that hazard.

**Two hours went into a test that could not run, and the reason is worth writing down.** The
`ListScreen` suite failed six ways with "`render` function has not been called", which reads
like a broken component and is not: **RNTL v14 renders asynchronously under React 19 act
semantics, so `render` must be awaited or `screen` is never populated.** The answer was
already in this repo, in a comment at the top of `primitives.test.tsx`, and the time was
lost to debugging the component instead of reading the neighbouring test first. Two blind
alleys on the way, each disproved rather than assumed: the explicit JSX type argument
`<ListScreen<Row>>` (innocent) and a missing `ThemeScope` (real, but not the cause). The
width-cap assertions were then mutation-checked by deleting the cap, and went red.

### The before/after measurement (2026-09-02, two EAS preview builds)

Two Android preview builds were made deliberately, so the comparison is real rather than
asserted: `7e4b546f` at `565fb11` (slices 1 and 2, NO virtualization) and `679da87c` at
`e45cca9` (with it). Both installed on the SM-S908B, five cold starts each via
`am start -W`, force-stopped between.

| | before | after |
|---|---|---|
| Cold start, `TotalTime` ms | 736, 649, 679, 704, 714 (median **704**) | 680, 657, 847, 781, 707 (median **707**) |
| APK size | 124,729,289 B | 124,733,389 B (**+4.1 KB**) |

**Cold start is unchanged, and that is the correct result rather than a disappointing one.**
The distributions overlap completely and the spread within each run is wider than the gap
between them. Virtualization does not touch app startup: it changes what a list costs to
mount and hold while you scroll it. Reporting a "win" here would have meant reading noise as
signal. The APK grew by 4 KB, which is the primitive and nothing else.

**THE MEASUREMENT THAT WOULD ACTUALLY SHOW THE BENEFIT COULD NOT BE TAKEN, and it is worth
being exact about why.** Every list this slice converted is empty in production: there are no
seeded testimonies, and the device has no signed-in account, so Family, MY-LIST, MY-POSTS and
the notification centre all render empty states. There is nothing to scroll, so there is no
memory or frame-timing difference to record. The one list with real data in production is
Watch, at 100 sermons, and Watch is deliberately NOT one of the converted screens.

So the honest state of this slice: the structural argument holds and is backed by the mobile
standard's "unbounded lists are always virtualized", the code is verified by 963 tests and by
the Family geometry on the device, the cost is 4 KB, and **the benefit is so far unmeasured**.
It becomes measurable the moment production has seeded content or a signed-in account on a
device, which `22` §3's cold-start seeding owes anyway.

### S4 · Tablet layouts and landscape · FOUNDATION LANDED (2026-09-02), layouts to come

**The foundation every one of the six frames needs is in and verified:**
- `src/lib/layout.ts`: `useLayout()` at `05`'s ~600dp. A hook rather than a constant, because
  it must answer again on every window change: a tablet rotates, and current Android can
  resize a free-form or split-screen window whenever it likes and ignores an orientation lock
  outright. 600dp is deliberately the same line Android's own `sw600dp` qualifier draws, so a
  device the platform calls a tablet and a device this app calls a tablet are the same device.
- `NavRail`, the mockup's `.railnav`, built from the frame's CSS read first-hand: 96 wide on
  card with a right hairline, a 46px gold logo, items 76 wide with 24px icons over an 11px
  bold label, the active one on a 10% blue wash, a spacer, then the avatar. It takes the SAME
  `TabItem` list as `TabBar`, so a root cannot exist in one and not the other, and it carries
  the same control-label rule (one line, 1.3x cap) for the same reason the bar does.
- `(tabs)/_layout.tsx` picks between them, and **the navigator's own `tabBarPosition` puts the
  rail on the left**. Worth recording that this was checked rather than assumed: the type is
  in the bottom-tabs definitions expo-router ships, so no wrapper or absolute positioning was
  needed and there is no second mechanism to keep in step.

**Verified on the REAL TABLET** (Galaxy Tab S10+ `SM-X826B`, 876dp portrait / 1400dp
landscape). It was first "verified" by forcing `TABLET_MIN_WIDTH` down to 300 on a phone,
which was the wrong instrument and Ayo said so: forcing the breakpoint proves the switch
fires, and proves nothing about how a layout looks at the width it was drawn for. The rail
draws correctly at real width, the bottom bar goes, content sits beside it, and the roots
navigate.

**THE TABLET IMMEDIATELY FOUND SOMETHING THE PHONE STRUCTURALLY COULD NOT: the rail
disappears on any pushed route.** It is rendered from the navigator's `tabBar` slot, so it
exists only on the five tab ROOTS. Open ACADEMY, a sermon, or any stack screen and a 1400dp
tablet is back to a single phone-shaped column with no navigation at all. Every tablet frame
in the mockup draws the rail, including `ACADEMY · tablet portrait`, which is a stack route.

So the rail belongs ABOVE the navigator rather than inside it, and that is a change to the
app's shell rather than to a screen. It also settles a question the remaining layouts would
each have had to answer separately, which is a good reason it surfaced before they were
built rather than after.

**A second thing the tablet settles:** the mockup's measures are per-frame AND per-orientation.
`.tcol` 600 is drawn for ACADEMY in tablet PORTRAIT; at 1400dp landscape the same 600 column
leaves most of the screen empty. Home shows the same thing more sharply, sitting as a 680
column in the middle of 1400dp with roughly 470dp of dead space either side. That is exactly
what `.dash` exists to fix, and it confirms the grid is load-bearing rather than decorative.

**Also worth recording, because it cost half an hour:** the tablet rendered a blank white
screen through four different diagnoses (old dev client, breakpoint probe, native fence,
uiautomator dump showing an empty root). The cause was none of them: **Metro had wedged** at
some point during the two EAS builds, still LISTENING on 8081 but no longer answering
`/status`, with connections in CLOSE_WAIT. The same load that had timed out three dashboard
test workers. The lesson is the one already in this repo's history, in a new costume: ASK THE
SYSTEM WHAT IT HOLDS. A `curl` against the dev server would have found it in ten seconds, and
the breakpoint probe I ran in the middle was meaningless because nothing was reloading.

**One drift caught and corrected on the way:** the frame's active rail item is a **10%** blue
wash and the nearest existing token was 5%. Neither `tonal.blue` (.12) nor `tonal.blueFaint`
(.05) is the frame's value, so `blueRail` (.10) and `bluePane` (.06, for the two-pane menu's
selected row) were added rather than rounding to something close. Same reasoning the repo
already applies to `redRow` and `redSoft`: nobody can see two points of alpha, and they are
kept apart because they mean different things and will drift the day one changes.

**The rail moved out of the tab navigator and into `TabletShell` (2026-09-02).** It is now a
sibling of the whole `Stack`, rendered in the root layout, with the tab navigator drawing no
bar at all above 600dp. A route-to-root map keeps the right item lit on a pushed screen, which
is what the ACADEMY frame shows by highlighting **More**, and splash/onboarding/auth stay
outside the shell because the app has no navigation to offer until somebody is past them.
Verified on the tablet in BOTH orientations: the rail persists on `/academy` with More lit.
The guarding tests were mutation-checked by reinstating the bar-slot version, and exactly the
two that assert survival went red.

**HOME's dashboard grid is built (2026-09-02).** `HomeDashboard` takes the six sections as
NAMED props rather than children: the phone order is load-bearing (`07`: the rhythm strip sits
directly under the service card) and a component that split `children` by index would reorder
the phone silently the first time a section moved. Two columns in tablet LANDSCAPE only, since
that is the only Home the mockup draws at tablet size, and `Screen` takes the `.dash` measure
of 1000 there instead of the 680 reading column.

**One thing in it needs Ayo's eye before it counts as done.** The frame places four sections
(hero and verse left; section title, sermon and sign-in right) and Home has six. "From the
family" and the member's rhythm strip are not placed by any frame, so they went to the right
column on the member frame's own hint that the rhythm belongs there. That is a design
judgement made in code, which is exactly the thing this repo's mockup-first rule exists to
prevent, so it is flagged rather than assumed.

**Ayo approved the column split on 2026-09-02** (left: service hero and verse, as the frame
draws; right: rhythm, From the family, Latest message, Join). The two tablet Home frames are
owed in `entry-flow.html` so the placement is recorded rather than implied by the code.

**A WRONG DIAGNOSIS, CORRECTED, and worth keeping because the wrong version was plausible.**
ACADEMY and WATCH both resolved to their error state on the tablet while Home showed a branch,
an address and service times, so this was written up as "specific to the courses and sermons
reads rather than to connectivity" and flagged as a possible PRODUCTION fault. It was nothing
of the sort. The dev env points at the LOCAL stack (`127.0.0.1:55321`) and only port 8081 had
been reverse-forwarded over adb, so the device could reach Metro and could not reach the
database at all.

What made the wrong answer so convincing is the thing worth remembering: **W1.1's bundled
branch snapshot did its job.** Home drew a real branch with a real address from the bundle
while every live read failed, which looks exactly like "some queries work and some do not".
An offline fallback that works perfectly is indistinguishable from a working backend until you
ask which rows came from where. `adb reverse tcp:55321 tcp:55321` and everything loaded.

**It also handed back the measurement S3 could not take.** With the local stack reachable the
seeded content is there, so the converted lists finally have rows on a device, and the WATCH
two-pane was verified against a hundred real sermons instead of an empty state.

**WATCH's two-pane is built and verified on the tablet (2026-09-02), and it is the pattern the
other two follow.** `TwoPane` is the mockup's `.twopane` (396 list, hairline, flexible detail);
`WatchListPane` is its `.pane-list`, drawing the SAME `SermonRow` from the SAME query as the
phone so the two cannot describe a sermon differently. **Routes stay the source of truth**: the
selected id is parsed from the PATH, so a notification deep link into a sermon lights the right
row for free, and back, gate-return and the deep links W3.6 verified all keep their meaning.
Landscape only, because 396 of list plus a player does not fit an 876dp portrait tablet.

**Two of my own defects, both caught on the device rather than by the suite:**
- The list header rendered the literal word **"title"**: `watch:title` never existed, and
  i18next falls back to the key's last segment, silently. Now `watch:paneTitle` ("Messages",
  the frame's own word) in all four locales. **This is exactly the class of bug W4.6's
  missing-key pass exists to catch**, and it argues for doing that pass with teeth.
- The selected-row wash was `blueRail` (.10) when the frame draws `.07`, and the margin was
  wrong. Corrected to the frame, and `bluePane` now carries this one meaning ("the row whose
  detail is showing") for both frames that draw it, rather than minting a third near-identical
  blue for a difference of one point of alpha.

**A BREAKPOINT BUG THE TESTS FOUND BEFORE THE DEVICE DID.** `isTablet` measured the CURRENT
width, while the doc comment claimed alignment with Android's `sw600dp`. `sw` is SMALLEST
width, and the difference matters: a large phone in landscape is over 1000dp wide, so it would
have been handed the rail and a two-pane sermon. The only screen this app lets a phone rotate
to is the player, where turning the device means "make the video bigger" and emphatically not
"spend 396dp on a list". Now `Math.min(width, height)`, so a phone stays a phone in both
orientations.

**Still to build:**
- FAMILY landscape feed plus detail, and FAMILY portrait single column plus rail. Both follow
  WATCH's pattern directly: a list pane over the existing feed query, the detail being the
  `/testimony/[id]` and `/prayer/[id]` routes that already exist.
- **SETTINGS menu plus pane is NOT the same shape and should not be attempted as if it were.**
  Its frame's left pane lists Appearance, Language, Notifications, Blocked members, Privacy and
  About as selectable sections, but three of those are not routes: the theme control is inline
  on `/settings`, and Privacy and About are links out to the website. Building the frame
  faithfully means giving Settings an information architecture it does not have, which changes
  the PHONE too. That is a product decision, not a layout one, and it is why WATCH was taken
  first instead.
- **The three master-detail layouts are architecturally the largest thing left in W4.7**,
  because a two-pane list does not PUSH a route when a row is tapped: it fills the detail pane
  instead. That touches deep links, back behaviour and the gate-return machine, none of which
  should be discovered late.
- ACADEMY and REGISTER want the frame's `.tcol` at **600**, while `Screen`'s only capped
  measure is **680**. The mockup carries at least four measures (`.tcol` 600, `.readwrap` 680,
  `.dash` 1000, `.tgrid` 1040) where the app has one, so the width class needs to grow before
  those two frames can be matched rather than approximated.
- The rail draws no avatar yet: `NavRail` takes one and `(tabs)/_layout.tsx` passes none, so a
  member sees the frame's `.rav` slot empty. Left until the layouts land rather than guessed.
- **Unlock orientation for the sermon player, and it needs a decision first.** `05` asks for
  landscape on the player and the reader specifically, not app-wide, so the implementation is
  a per-screen request via `expo-screen-orientation`. That is a NEW NATIVE DEPENDENCY: adding
  it needs Ayo's approval under the project's dependency rule, and it crashes every existing
  dev client until an EAS rebuild (the dev-client native fence). The blunt alternative,
  `orientation: 'default'` in `app.config.js`, is a bigger product change than `05` asks,
  because it lets every screen on a phone rotate and so every screen would need verifying in
  landscape. Not taken unilaterally. Note that on a real tablet the point is partly moot
