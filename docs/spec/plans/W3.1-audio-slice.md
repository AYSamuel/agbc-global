# W3.1 · Audio slice

Build blueprint for Phase 3's first item. Behavioral truth is `08`; the data is `02`
(§Storage buckets, §sermons); the dashboard side is `17` §4. This doc carries the decisions
taken with Ayo, the slice order, the contract each slice leaves for the next, and the gates.
**Delete once W3.1 lands.**

## Decisions taken with Ayo (2026-08-14)

1. **The bucket is PRIVATE; playback URLs are signed with a 24-hour TTL, minted on player
   open.** `02` left `sermon-audio` open ("public-read or modest-TTL signed"); Ayo's call,
   made knowing the trade: sermon audios are the church's own uploads (some will never be on
   YouTube at all), so a link copied out of the app's traffic goes dead within a day instead
   of becoming a permanent free door. 24 hours cannot expire mid-listen (a URL minted on open
   outlives any single session, background included), and reopening mints a fresh one, so
   background playback and resume are unaffected. Guests still listen: the SELECT policy that
   gates minting covers `anon` too. This is a fence against casual spread, not a vault:
   nothing short of DRM stops a determined listener from keeping audio they can play, and
   that is disproportionate for sermons. `02` and `08` are synced in the slice-1 PR.
2. **The dashboard upload lands NOW, in W3.1, not Dashboard Phase C.** `25` and `17`'s
   phasing note conflicted; Ayo picked W3.1 (the "listen while driving" promise has no
   supply line without it, and the media team's weekly upload task needs the tool before
   launch). `17`'s phasing note is amended in the same PR.
3. **`sermons.audio_url` is renamed to `audio_path`.** Same reasoning and same safety
   argument as `testimonies.image_url` → `image_path` (W2.3): a signed URL expires, so what
   belongs on the row is the object path; and the column has never held a value in any
   environment (no seed sets it, the sync's field policy never touches it, prod has no app
   schema yet), so a straight rename costs nothing now and a release cycle later.

## Slice order

**1a · The shelf (backend unit, this session).** Migration: the `sermon-audio` bucket row
(private, 150 MiB cap, `audio/mpeg` + `audio/mp4` + `audio/aac` + `audio/x-m4a`), storage
policies (below), the `audio_path` rename, and the dangling-reference guard. pgTAP `034`.
Local `[storage] file_size_limit` raised (50 MiB would refuse a normal sermon). Types
regenerated; the four mobile call sites follow the rename. Spec syncs per decisions 1-3.

**1b · The dashboard module (frame gate, then code).** Frames composed in
`design/mockups/dashboard.html` (house rule: no dashboard surface is built without an
approved frame; the four states are surfaces too) covering BOTH flows: attach audio to a
synced sermon, and create a manual audio-only sermon (`youtube_id` null; the schema and the
player's `audioOnlyPending` state have supported this since W1.3, and it is exactly the
"our own audios, not on YouTube" case Ayo raised). Then the module: `manage_sermon_audio`
as an admin-only `DashboardAction`, upload direct from the browser to Storage under the
admin's own JWT (a 60 MiB file must not ride through a server action; storage RLS is the
gate), then an attach server action that re-authorizes, **magic-byte checks the uploaded
object** (signed URL + `Range: bytes=0-11`, never the client's Content-Type), and writes
`audio_path` + metadata (`speaker`, `series`, `duration_sec`) to the row. Replace =
new object + delete old, write-once like `testimony-photos`; remove clears the column
BEFORE deleting the object (the guard forbids the other order). Vitest server tests against
the local stack + the IDOR/refusal matrix.

**2 · The native rebuild (decisions taken 2026-08-14, with Ayo).** `expo-audio` ~57.0.3
with `{ enableBackgroundPlayback: true, recordAudioAndroid: false, microphonePermission:
false }` (the app plays and never records; option names verified against the installed
plugin source), **plus `expo-notifications` ~57.0.10, bare**: Ayo approved carrying the
push module's native half on this same build so W3.3 needs no second rebuild (the W2.10
Sentry trick); its icon, color and channels stay W3.3's decisions. No import guards are
needed: slice 2 adds no imports, and the player code (slice 3) lands only after the
rebuilt client is installed, so no old client ever loads a screen that touches the new
modules. **The rebuild is Android-only for now**: there is no iPhone in the project (the
`18` launch checklist already carries the iOS half), so the iOS dev build waits for a
device to exist. Install on the physical Android over adb.

**3 · The player (landed 2026-08-14).** The engine (`setAudioModeAsync` playsInSilentMode +
shouldPlayInBackground + doNotMix; `setActiveForLockScreen` with title/artist/artwork,
mandatory on Android), the audio-only toggle, ±15s, speed 1x/1.25x/1.5x, and the
server-synced resume layer: throttled `playback_positions` writes (~10s, plus
pause/exit/background) and the seek on open (within-30s-of-end = start over, under 15s =
not worth restoring, `08`). Signed URL minted on open, re-minted once on a playback error.

Six decisions taken while building it, each synced into `08` or `05` in the same PR:

1. **The newer stored position wins, not the server's.** `08` said "seek to the server
   position when signed in, else the local one", which rewinds a real member: listen
   offline through a flight while every server write fails and the device layer keeps
   saving, then land, reopen, and a blind server read hands back the position from before
   takeoff. `preferredPosition` takes the later `updated_at`, and `08` line 23 now says so.
2. **The position is per member and message, not per mode.** The video path writes the same
   `playback_positions` row, so half a message watched on a tablet resumes in the car.
   Without this, cross-device resume would have silently worked for audio only.
3. **Speed took the mockup Download tile's slot** (approved with Ayo before the frames were
   composed): `08` never specified a download, that tile had sat dimmed since W1.3, and
   speed had no home in any frame.
4. **A dimmed tile still answers a tap.** `08` asks the unavailable toggle to carry a
   tooltip; a control that announces itself `disabled` while it still responds is lying to
   assistive tech, so the three refusals are an `accessibilityHint` on focus plus a toast
   on press, and `accessibilityState.disabled` is gone.
5. **Leaving the SCREEN stops the audio; backgrounding the app does not.** The device found
   the bug: a deep link to a second message pushes a new screen and leaves the first one
   mounted, so its sermon kept playing underneath a player showing something else, with no
   control for it anywhere in the app (only the notification shade). `useFocusEffect`'s
   cleanup is exactly the right seam, because navigation blurs a screen and backgrounding
   does not. It pauses rather than releases, so coming back finds the message where it was
   left. Both halves are verified on the device: pushing a second message froze the first at
   2:44, and backgrounding with the screen off ran 2:44 to 5:27.
6. **Every tile reserves the value line, blank where there is nothing to say**
   (Ayo's report on the built screen). A row of three stretches to its tallest member, and
   only Speed carries a value, so the other two centred their contents against a different
   number of lines and the three icons sat at two different heights across one row. The
   frames carry the same reserved line, so frame and build still agree.

**Two errors the verification caught that reading the code would not have.** The artwork
scrim was tuned twice: 58% made the dimmed thumbnail identical to the no-thumbnail fallback
beside it (caught in the Chrome render), and 30% did not read as dimmed at all behind a real
photo (caught on the device, because the mockup's placeholder is a flat gradient and a
YouTube thumbnail is a bright picture). It sits at 45%. And `skipTarget` clamped a
backward skip to a NEGATIVE ceiling while the duration was still unknown, so back-15 in the
opening seconds of a stream sought below zero; the pure test caught it.

**And one the blur fix itself introduced:** its cleanup also runs on unmount, where
expo-audio has already released the player, so `player.pause()` threw "Cannot use shared
object that was already released" and took the screen down on every back-press out of the
player. The guard is a try/catch with the reason written next to it, and
`src/test/expoAudio.ts` now MODELS the release (calls into a released player throw, and the
fake registers its release effect first, exactly as `useReleasingSharedObject` does), so the
guard is load-bearing in the suite rather than only on the device.

**And one the review caught after the device work** (2026-08-14): the screen's re-mint
callback was keyed on the query RESULT object, whose identity moves with every
fetch-state change, while the player status it reacts to stays the OLD player's error
until the new player reports. So the moment the fresh URL arrived, the error effect
re-ran, counted the one silent re-mint as spent, and put the failure screen over a
source that was about to play. The unit suite could not see it because the mocked query
result was referentially stable; the regression test now hands the screen a NEW result
object mid-re-mint, the way React Query actually does. The fix keys the callback on
`refetch`, which the observer binds once.

**Not built, deliberately:** the scrub takes no drag. The frame draws no handle, `08`'s seek
is the ±15s pair, and that pair is also the tap alternative a drag would have owed.

**Dev seed audio (the open gate from 1b) is closed:** `scripts/seed-local-audio.mjs`
generates a 12-minute tone MP3 with ffmpeg, uploads it to the local bucket and stamps the two
newest sermons, wired into `pnpm db:reset` and available as `pnpm db:seed-audio`. Nothing is
committed: 12 minutes is ~5.5 MB, and a two-second placeholder could not test `08`'s
ten-minute background criterion. Without ffmpeg it skips with a note rather than failing.

**4 · The member surfaces (landed 2026-08-15).** Save (gate + `saved_items`), MY-LIST,
SERMON-NOTES (autosave), all against existing W1.3 tables; four states each; frames approved
at the gate. Verified on the device in both themes, at 1.3x and 2.0x text scale, and at
tablet width (density override), including the offline write and its recovery.

Three decisions taken while building it, beyond the six at the frame gate:

1. **On `sermon_notes` and `saved_items`, identity stopped being an input**
   (`20260815120000`). The repo had two precedents for owning a row: RLS alone (W1.3, which
   lets a client claim an identity and then checks the claim) and a guard trigger that
   overwrites `profile_id` (`rsvps`, which is right there because that trigger also forces
   status and the reminder schedule). These two tables have nothing else to force, so a
   trigger would exist only to assign one column: `profile_id` now DEFAULTS to `auth.uid()`
   and the INSERT grant excludes it, which turns "your forgery is refused" into "identity is
   not something you can send". The same migration replaces #96's blanket privileges with
   column-scoped grants (the first INSERT-side use of the `20260803140000` mechanism) and
   adds the unique index decision 6 asked for. Proven twice: pgTAP `035` for the matrix, and
   the real PostgREST road for the exact request shapes supabase-js sends, because a
   privilege proven in pgTAP is not yet proven through PostgREST.
2. **Notes are NOT queued.** Save joins the write queue as `saved` (decision 4), but the
   notes editor keeps its own debounce plus a persisted draft: `01` §8 keeps composition out
   of the queue, and the queue's end-state-per-entity model would be the wrong shape for a
   document that supersedes itself on every keystroke. `01` §8's own list was corrected in
   the same PR for the same reason: it named "playback position" as queued, which W3.1 slice
   3 had already built as a throttled direct write.
3. **The editor opens on an ANSWER, not on a query.** The screen mounts it only once the
   read has come back (or failed with a draft in hand), so the opening copy is decided in a
   lazy initializer instead of an effect that would setState synchronously on arrival. The
   React Compiler's lint rules asked for this and the shape is better for it: the hook has no
   "not ready yet" state to render, and the retry became a plain effect keyed on the status.
   The same pass replaced `flush`'s self-recursion with a loop.

**One trap the device caught that the suite could not.** A failed read with NO draft must not
open an empty page: its autosave would overwrite the very document the app could not fetch.
The editor now opens blind only when a draft is the newer copy, and the error state stands
otherwise. The same shape of race lives in the draft store itself, which rehydrates
asynchronously: the screen waits for `useDraftsHydrated()` before mounting the editor,
because the editor decides its opening copy exactly once and "no draft yet" would have been
the wrong answer to decide on.

**Two more, taken with Ayo after seeing it on the device (2026-08-15):**

1. **The message's title is the subject of the screen, not a label.** It began as the frame's
   11px uppercase gold eyebrow, which a real synced title ("DAY 14: Disciples believed it was
   real, But only one asked to Experience it") turned into the hardest thing on the page to
   read. It is now 20px bold, and the frame was updated in the same change. It KEEPS the gold:
   at 20px bold the text is WCAG "large" (>= 18.66px bold), where the bar is 3:1 rather than
   4.5:1, and `--eye`'s deep gold on cream clears that comfortably. At the 16px tried first it
   would not have, which is a useful reminder that size and colour hold each other up.
2. **Note drafts are encrypted at rest**, on `LargeSecureStore` (the adapter the Supabase
   session already uses: an AES-256 key per write in Keychain/Keystore, ciphertext in
   AsyncStorage). A draft is somebody's reflection on a sermon, which is religious belief
   about a named person and therefore GDPR Art. 9 special-category data; `20` treats this app
   as higher-stakes for that reason, and plaintext on disk was the one place in this slice
   where that did not hold. Measured on the device afterwards: typing is unaffected, and the
   draft is durable within about a second rather than instantly (killing the app in the same
   breath as the last keystroke still loses it, a second later does not).

Decisions taken at the frame gate, before any screen code (2026-08-14, with Ayo):

1. **SERMON-NOTES is ONE document, autosaved**, not the timestamped cards the frame drew.
   `sermon_notes` holds one body per member per message (`02`) and `08` autosaves it, so the
   cards were a data shape the database does not have. The timestamps survive as text the
   Add button writes into the page. The frame was recomposed; the Save button became the
   autosave status, because a promise to save with nothing on screen is uncheckable.
2. **Opening notes pauses the message** (the player pauses on blur since slice 3), which is
   why the Add line can name one fixed second.
3. **Save lives in the player's top bar** beside Share, plus a remove control on each
   MY-LIST row. Card-level Save is deliberately not built, like the card progress bar `08`
   asks for and W1.3 left out.
4. **Save is queued like Glory** (`saved` joins the write-queue kinds; `01` §8's list gets
   it in the same PR), so a tap on the Underground lands when the signal comes back.
5. **Notes keep a persisted local draft**, so writing offline is never lost.
6. `sermon_notes` gets its missing `unique (profile_id, sermon_id)`: "one document per
   member per message" was a comment, not a constraint, and an autosaving editor on two
   devices would otherwise split a member's notes across two rows with one silently winning.

**And a redesign that arrived with the gate.** Ayo rejected the three-tile control row on
sight, so three directions were drawn in the mockup and **A** was chosen: mode becomes a
segmented `Video | Audio` control, Speed and Notes become quiet actions under it, Speed is
absent (not dimmed) in video mode, and Open on YouTube becomes a text link. `SegmentedControl`
in the shared library gained icons and an unavailable-but-answerable state rather than the
screen growing a private copy. Two things the device caught on the way: the player was
wearing the settings-screen header instead of the frame's quiet `NOW PLAYING` eyebrow (fixed
via `AppHeader`'s new `titleStyle`), and the video state printed "1x" under a greyed Speed.
The video state's YouTube attribution line went with it (`08` synced): the embed carries
YouTube's own branding, so the line only repeated it. Audio keeps its line.

## The storage contract (what 1a leaves behind)

- Bucket `sermon-audio`: private, `file_size_limit` 157286400 (150 MiB), mimes
  `audio/mpeg`, `audio/mp4`, `audio/aac`, `audio/x-m4a`.
- INSERT/DELETE: live-table admins only (`caller_is_admin_live()`), `aal2` sessions only
  (safe here where it was NOT safe on content tables: no mobile member ever writes this
  bucket, so the claim check locks nobody out), object names forced to `<uuid>.<ext>`
  (random ids per `02`, no path traversal, no PII in names). No UPDATE policy: objects are
  write-once, replacement is a new object.
- SELECT: `anon` + `authenticated`, the whole bucket. This IS the mint permission for the
  24h signed URLs, guests included. No status gating by design: `08`'s rot handling keeps
  audio playable when the YouTube half of a sermon vanishes.
- `sermons.audio_path` may only reference an object that exists in the bucket (trigger
  guard, service-role writes exempt like every guard in this repo). Clear the column first
  when removing audio.

**5 · Message artwork (added 2026-08-15, Ayo's ask, after slice 4).** A message created in
the dashboard has no picture anywhere: `sermonAudio.ts` inserts title, speaker, series, date,
`audio_path` and duration and nothing else, so `thumbnail_url` stays empty, the player draws the
branded gradient, the lock screen gets no art, and the Watch rails show a blank navy card.
The shape: a `sermon-artwork` bucket and a NEW column (`artwork_path`), never `thumbnail_url`,
which the nightly sync owns and would overwrite; upload in both dashboard panels with the
magic-byte check the audio upload already does; the app preferring our artwork over the
YouTube thumbnail in `SermonArtwork`, `SermonRow` and the lock-screen metadata. Frames first,
as ever. A second prize worth naming: a message whose artwork AND title are ours needs no
YouTube attribution at all, because nothing on that screen is theirs.
